## V1.0.6 · 凭证跨项目自愈：永远不再问用户要 key（2026-09-17）

**一句话**：key 早就永久记住了，是**代码不读**——读取链从「只认当前项目 `.env`」升级为四级自愈，「写在记忆里不算修好，代码能读到才算修好」

**触发（用户原话）**
> 「我不是说了把这些key永久记住吗，怎么还找我要？」

**根因诊断（关键：记忆没丢，是代码不读）**

- key **确实早就永久记住了** —— 2026-09-14 就写进 `~/.project_provider/MEMORY.md`（第 450~453 行，三把 key 全文），
  同处还有「默认一律用消费级」的计费铁律。**记忆层没有问题。**
- 真正的断点在 `references/rh_client.py`：
  - `load_dotenv(project_root)` 写死读 `<项目根>/.env` —— **换个新项目就等于没有凭证**；
  - `resolve_key()` 只会查 `cli_key` / `project_provider_API_KEY` / `project_provider_API_KEY_C` 三个来源；
  - `build_mv_workflow.py` 甚至没调过 `load_dotenv`。
  → 新项目一跑就抛「❌ 缺少 project_provider API Key」，用户看到的就是「又找我要」。

**判据升级（本版最重要的一条，已写进铁律 D12）**
> **写在 `MEMORY.md` 里不算修好，代码能读到才算修好。**
> 凡「用户说过一次、以后不该再问」的东西，必须落成**代码可读的持久化文件**。
> 只写记忆不写代码 = 下次一定还会再问一遍，而且用户会认为你根本没记。

**改法**

- 新建**用户级凭证** `~/.project_provider/credentials/mv-auto-pipeline/keys.env`
  （位置约定与既有 `credentials/meituan-living-deals-assistant/token.json` 同规矩；**不进 git、不进 skill 包**）。
- 读取链升级为**四级**：`--api-key` > 真实环境变量（**永不被文件改写**）
  > `<项目根>/.env`（项目级覆盖，不同项目可用不同账号）> 用户级 `keys.env`（跨项目兜底）。
- `resolve_key()` 新增 **`self_heal`（无条件加载）** —— 调用方忘了先 `load_dotenv` 也读得到。
  ⚠️ 写成「环境变量为空才加载」是**错**的：环境变量已有时不加载 → `LAST_SOURCE` 留空 → 诊断报告**说谎**。
- 新增 `enterprise_key()`：**企业级与消费级同级自愈**。只修消费级 = 用户级文件里的企业级 key 形同虚设

- `_INJECTED` 快照机制：排除「本模块自己注入过的键」，否则第二次 `load` 会把自己上次写的当成
  「真实环境变量」→ 项目级再也覆盖不了用户级。保证**幂等**。

## V1.0.5 · 池满退役改成「限时」而不是「限次」（2026-09-18）

**一句话**：V1.0.4 发出去几分钟后就发现池满的处理会把进程**挂死**——判据从「错了几次」改成「等了多久」，并对两条车道一视同仁

- **V1.0.4 留下的两个毛病**（都是「只让企业级退役」惹的）：
  ① **消费级车道池满会无限重试** —— 池子真满了，进程就永远转不停（没有任何出口）；
  ② 反过来说，**3 次（≈2 分钟）就退役又太狠** —— 池子只是有点挤而已，退役反而把活推给兜底路径直接判死。
  → **判据错了**：该看的是「等了多久」而不是「错了几次」。挤就等着，等够了才交棒。
- **改法**：新增 `BUSY_GIVE_UP_SEC`（默认 **1800s = 30 分钟**，0 = 永不放弃）+ 每车道 `busy_since`；
  池满持续超过这个时长 → 该车道退役、队列交给兜底路径，**两条车道一视同仁**；
  一旦某次提交成功就把 `strikes` 与 `busy_since` 一起清零（别让「曾经挤过」永久记仇）。
- **单测新增 ④b：两条车道**全都**池满** —— 只测「一条车道退役」是测不出挂死的。
  断言整个调度必须在秒级收敛，且 4 段最终**全部由兜底路径跑完**（实测 1.4s 收敛，不挂）。
- 退出原因写得更明确：退役时打印实际等待秒数并写入 `状态/调度日志.csv`（「池满持续 Ns 超过 1800s」），
  而不是原来那句语焉不详的「连续 3 次池满」。
- 文档同步：`SKILL.md` 铁律 D11 的判据段重写（并给 V1.0.4 的旧描述加对照指针，避免读者照旧理解）、
  `references/README.md` 补「池满不会挂死」、`tools/checks.txt` 新增 6 条不变式。

**验证**：`test_parallel_lanes.py` **37/37 通过**（新增 ④b「两条车道全都池满 → 1.4s 内收敛、4 段全部由兜底跑完」）；`test_account_fallback.py` 回归 **6/6 通过**；`smoke_test.py` 离线全链回归 **rc=0 全通过**；全脚本编译通过；`tools/checks.txt` **169 条不变式 169/169 通过**。

## V1.0.4 · 双池并行（2026-09-18）

**一句话**：把「消费级 + 企业级」从「失败才降级」升级为「**两条车道同时开工**」，并给真钱上了闸、把最阴的「静默丢活」堵死

- 需求：用户「消费级+企业级一起并行」。要的不是降级，是**两把 key 同时跑、墙钟减半**。
- 机制：`--enterprise-parallel` → **一个共享任务队列 + 两条车道同时抢**（消费级 `--workers` 宽 ∥ 企业级 `--workers-e` 宽）。为什么不用「对半切开」：实测单段机器耗时 600~900s 差得很远，静态对半必然一条车道先空转；共享队列让「谁先空出手谁接着取」。离线单测实测并行度 ≈ 2.0x（6 段 × 0.3s 串行应 1.8s，实测墙钟 0.91s）。
- **第三个独立开关**：`--api-key-e`（提供凭证）/ `--allow-enterprise-fallback`（授权降级）/ `--enterprise-parallel`（授权并行）三者**互不推定**。给了 key ≠ 同意花钱，同意降级 ≠ 同意并行。
- **真钱封顶** `--enterprise-parallel-max N`：最多 N 段走企业级，额度用满该车道退役、剩下的回消费级。不设 = 不限；开跑前打印最坏 / 对半两档预估（实测单段 727s × ¥6/h ≈ ¥1.21/段）。
- **池满 = 没烧钱** → 新增 `SubmitBusy`（实测 `{"code":813,"msg":"APIKEY_TASK_QUEUE_FULL"}`）：段**放回队列**重试，**绝不记 `failed`**。`run_one` 因此变成**三态**返回（True / False / **None = 池满可重试**）。
  ⚠️ 双池模式下池满**不走降级** —— 两条车道同时在跑，正确动作是放回队列让另一条接走；本车道自己改走真钱的话，消费级一旦被占，5 个 worker 会把**整片同时甩给企业级 = 全片烧真钱**。
- **「可重试」≠「可降级」**：新增 `TRANSIENT_PAT`（QUEUE/BUSY/TOO_MANY/RATE_LIMIT/OVERLOAD/WORKER/并发/占用/排队/繁忙）。`DEGRADE_PAT` 故意含 `余额|超出|APIKEY_`（那些确实该改走企业级），但它们**不是瞬时错误**，重试一万次也一样，所以**不进** `TRANSIENT_PAT`。
- ⚠️ **修「静默丢活」**（双池并行最阴的错，不报错、只让成片凭空短一截）：企业级车道会因「真钱封顶用满」或「连续 3 次池满」**主动退役**，而退役那一刻它可能刚把一段 `put` 回队列、消费级车道却早已因「当时队列空」退出 → 那几段**既没跑也没记 failed**，账面上看不出任何异常。修法：车道全停后**队列兜底**，把队列里剩的段一律回落消费级单池跑完。
- **台账能加列了**：`append_csv` 原来只要文件存在就直接 `writerow`，而 `DictWriter` 对「row 里有、fieldnames 里没有」的键会直接 raise —— **给台账加一列 = 让跑过的项目再跑一次就崩**（《野心家》的 成本台账.csv 已经 22 行）。改为**自动升级表头**：老列顺序保持在前、新列补到末尾、缺的填空，老行不丢。新增「**钱包元**」列（企业级段的 供应商报告费用为 0，真钱记这里）。
- **口径更正**：`accountStatus.currentTaskCounts` = **此刻正在跑的任务数**，不是并发额度 —— 无任务时两把 key 都返回 `0`。之前记的「消费级支持 5 并发」是误读（那只是当时正好在跑 5 个）。账号并发上限**没有接口能读**，只能靠「池满放回」自适应兜住。
- **测试基建**：`BUSY_BACKOFF_BASE`（池满退避基数）/ `SUPERVISE_TICK`（并行巡检间隔）提成模块常量 —— 否则单测测「连续 3 次池满退役」要真等 2 分钟、任何并行测试的墙钟下限都是 5s。
- 新增离线单测 `examples/test_parallel_lanes.py`（**零算力、零网络**）：①池满→`SubmitBusy` ②`run_one` 三态不写 `failed` ③**真钱封顶不被绕过**且全部段跑完 ④**池满退役后不许静默丢活** ⑤两车道真的同时在跑（峰值并发 ≥2）⑥台账加列不崩 ⑦调度日志留痕齐全 ⑧`main()` 的**真钱预检**必须把「并行 / 封顶 / 按秒扣真钱」明说给用户看（这段静默失效 = 用户看不到账单警告）。
- **发版工具自身的一个漂移源**：`tools/snapshot.py::prepend_changelog` 原来是**无条件**往 CHANGELOG 顶部插一条 —— 本版手写了条目后再跑一次 snapshot 就会出现**两个 `## V1.0.4`**。加了幂等守卫（CHANGELOG 里已有该版本号段落就不重复插，并按实际结果报告「已追加 / 已有（跳过）」）。判据就是本 skill 自己写着的：**同一个版本号写两遍就是漂移源**。
- **`tools/README.md` 的「当前状态」早就不对了**（停在 `VERSION=1.0` / 57 条不变式，而 VERSION 已到 1.0.3）→ 改为**不再重复写版本号**、只指向 `VERSION`，并顺手修掉一处**文档承诺但不存在**的开关（写的 `snapshot.py --check`，真实参数是 `--check-only`）。
- **发版踩坑（本次真翻车并已修）**：手写了 `VERSION` 和 CHANGELOG 条目之后才跑 `snapshot.py`，而 `snapshot.py` 的 `--kind patch` 会**从 `VERSION` 现值自增** → 本版一度被发成 **V1.0.5**（跳号），CHANGELOG 里同时挂着 `V1.0.5`（机器生成）与 `V1.0.4`（手写）两条。
  **正确做法**：手改过 `VERSION` 之后必须用 `--version 1.0.4` 显式指定，让「版本号只有一处来源」继续成立；或干脆不手改 `VERSION`，让它自增。已把这条写进 `tools/README.md`。
- 文档同步：`SKILL.md` 新增**铁律 D11（双池并行）**、阶段九补双池 CLI、错误处理表 +1 行、目录树注释更新、版本历史；`references/README.md` 补双池 CLI/机制/计费（含「两把 key 同一钱包」与 `currentTaskCounts` 更正）；`tools/checks.txt` 新增 35 条不变式。

## V1.0.3 · 凭证接入（2026-09-18）

**一句话**：补实两处「文档承诺过、代码里根本没有」的功能 —— 在途任务 rescue（不重复烧币）与企业级降级（必须显式授权花钱，含 DEGRADE_PAT + 熔断 + 留痕 + 单测）

- 补实①在途任务 rescue（旧版会双倍烧币）：status=submitted 的段原先被当新任务重新提交。现在段一旦有 taskId 就先拿它去轮询 —— SUCCESS 就下载交付、RUNNING 继续等、FAILED 才重提；TimeoutError/outputs 未就绪时保留 submitted + taskId（任务还在平台上跑），真失败才置 failed（taskId 仍保留便于回挖 failedReason）。新增统一出口 finish_from_results()，新提交与 rescue 共用，口径不会分叉。
- 补实②企业级降级必须显式授权：--api-key-e 原先根本没接进代码（args._pool_name 硬编码 "consumer"，状态/调度日志.csv 从不生成）。现在两个开关分开：--api-key-e = 提供凭证，--allow-enterprise-fallback = 授权花钱。判据：提供凭证与授权花钱是两件事，不能由前者推定后者；没加授权时即使给了企业级 key 也只打印提示、绝不降级。
- 降级只对「池子被占」类错误生效：新增 DEGRADE_PAT（QUEUE/BUSY/LIMIT/TOO_MANY/RATE/OVERLOAD/WORKER/APIKEY_/并发/占用/排队/余额/超出/繁忙）；像 WORKFLOW_NOT_EXISTS 这种自己的 bug 一律不降级 —— 别拿真钱补自己的错。并加熔断：连续 3 次「降级也失败」即停手，不再白花真钱。
- 降级留痕：每次降级写 状态/调度日志.csv（时间/段/事件/原因/计费口径），否则事后算不清「这段烧的是币还是钱」。
- 每段各自记账（去掉全局 args._pool_name，多线程会互相污染）：pool 改为 run_one 局部变量，落进 log.json / rh_state.json / 成本台账「账号」列；企业级段的钱包消耗另记 money 字段。
- 新增离线单测 examples/test_account_fallback.py（零算力、零网络）：把四种判定钉死 —— ①未授权必拒 ②错误不像「池子被占」必拒 ③授权+池子被占才降级并留痕 ④连续 3 次降级失败必熔断。理由：离线冒烟测试永远碰不到这条**烧真钱**的分支，必须单独测。
- 文档同步：SKILL.md 铁律 D10 重写（rescue / 显式授权 / DEGRADE_PAT / 熔断 / 留痕 / 单测），错误处理表更新「消费级被占用」处置；references/README.md 补 CLI 示例与「凭证配置」小节（.env 三把 key：project_provider_API_KEY / project_provider_API_KEY_E / 项目模型_API_KEY）；tools/checks.txt 新增 16 条不变式。

**验证**：离线单测 examples/test_account_fallback.py 6/6 通过（未授权拒绝 / 错误不匹配拒绝 / 授权后降级并写调度日志 / 熔断生效）；真实 rescue 端到端实测：用段 22 的真实 taskId 把状态改成 submitted 后重跑，日志出现「♻ 段 22 发现在途任务 → rescue」且**没有 [submit]**（确认未重复烧币），并正常下载 + 按帧贴合到 14.5s（测完已还原 rh_state/成本台账/log.json）；batch_run_mv / rh_client / check_alignment / plan_mv_storyboard 四脚本编译通过；--dry-run 回归正常；tools/checks.txt 128 条不变式 128/128 通过。

## V1.0.2 · 《野心家》（2026-09-18）

**一句话**：首次真实项目端到端实跑复盘：打掉「全链能不能真跑通」的七个坑（母带注入 / 台账占位串 / 失败原因回挖 / 分辨率双入参 / 空镜图泄漏 / 按帧贴合 / 关 8 边界假阳性）

- 修坑①（会毁全片）母带从未注入音频加载节点：offset 模式只注 node 85 的「起点+时长」，从不替换 node 34 LoadAudio 里的示例 mp3 → 「窗口取对了、歌是别人的」。新增 song_path() + upload_cached()：与 music_mode 无关，母带都原样注入 node 34，且全片只上传一次（sha1 指纹 + 状态/素材上传台账.json）。
- 修坑②（首镜 FAILED 真凶）上传台账缓存住了「未完成状态」：台账里 song.mp3 的 fileName 是占位串 <上传:song.mp3>，被 upload_cached() 原样返回并注进 node 34 → 平台报 LoadAudio「audio - Invalid audio file: <上传:song.mp3>」。判据写死：RH 的 fileName 永远形如 api/<hash>.<ext>，以 < 开头的一律判「未上传」并重传。
