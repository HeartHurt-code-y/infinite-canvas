# 2026-08-24 工作日志

## 修复：供应商模型保存报 "must be scoped to its provider connection"（root cause）

**现象**：供应商设置拉取模型并配置用途后，点「保存图片与视频模型」报 validation 错误：
`selected model definition must be scoped to its provider connection`，modelDefinitionId 为裸 ID（如 `doubao-seedance-2-0-260128`），期望 `remote::{provider}::{remote_model_id}`。

**根因链**（三层）：
1. 早期版本/种子数据允许把裸远程模型 ID 直接存为 `model_definitions.id` + `provider_model_bindings.model_definition_id`（DB 实证存在裸 ID 绑定）。
2. 前端 restore 路径 `loadSavedProviderModels` 用 `definition.id` 返回 modelDefinitionId（裸 ID），保存时 `handleSaveModels` 原样透传。
3. 后端 `validate_model_selections`（commands.rs:607-621）要求严格 scoped 格式，裸 ID 被拒。

**修复**（三层，surgical）：
1. **后端数据迁移**：`Storage::open` 新增 `migrate_legacy_model_bindings()`（storage.rs），把非规范格式 binding 重写为 `remote::{provider}::{remote_model_id}`，并同步创建/更新 scoped definition（保留旧 definition 行防破坏任务快照）。幂等，每次启动执行。
2. **前端 restore 规范化**：`backend.ts` 新增 `providerScopedModelDefinitionId()`，`loadSavedProviderModels` 不信任历史 definition.id，一律构造 scoped ID。
3. **前端保存强制 scoped**：`ProviderSettingsDialog.handleSaveModels` 用 `providerScopedModelDefinitionId(draft.id, model.id)` 构造，杜绝透传脏数据。

**验证**：Rust 42 测试（含新迁移测试）、前端 62 测试（含 restore 裸 ID → 保存 scoped 回归测试）、typecheck、eslint、cargo fmt、clippy 全通过。DB 实证：用户 DB 的 binding 已在排查期间被 fetch 路径保存自愈为 scoped（时间戳 1787534567042）；迁移对真实数据幂等（0 迁移）。

**经验**：模型定义 ID 的 `remote::{provider}::{model}` 作用域是全局约定（model_schema.rs:14）；前端所有构造/透传点必须与后端 `provider_scoped_model_definition_id` 对齐，保存类操作不要信任来源 ID。

## 修复：供应商模型保存报 "model operation parameters must be a JSON object"（Bug 2）

**现象**：Bug 1（scoped ID）修复后，保存流穿过 scoping 校验，下一关 `validate_schema_for_operations` 报
`model operation parameters must be a JSON object`，details `{ definition: { resultType: "video" }, operation: "video_generation" }`。

**根因链**：
1. 报错前 Bug 1 的 scoping 校验一直先于 schema 校验失败，所以**历史畸形 schema 从未被触碰**——只是被前一道校验挡住。
2. 实时 DB 实证：`model_definitions` 中 `remote::provider-6a826365-…::doubao-seedance-2.5`（从真实 API 拉取，非 seed 的 `doubao-seedance-2-5-260628`）的 `operations_json` 是畸形三段式
   `{ image_to_image:{resultType:"image"}, text_to_image:{resultType:"image"}, video_generation:{resultType:"video"} }`——每个操作只有 `resultType`，**缺失 `parameters`/`requestProfileId`/`request`**。
3. `schema_for_enabled_operations`（model_schema.rs:57）一旦在 discovered 里找到该操作的 object 就**原样采用**，不补 `parameters`；于是 `validate_schema_for_operations`（:159-167）的 `.and_then(Value::as_object)` 返回 None → 报 "parameters must be a JSON object"。
4. 校验在存储之前失败，DB 永远停在畸形，每次保存循环失败。另有一条孤儿 `remote::doubao-seedance-2.5`（缺 provider 段、无绑定引用）也是历史遗留。
5. 注意：`default_operation_schema` / `infer_catalog_schema` 永远产出含 `parameters` 的合法 schema，故畸形只能源于**早期落库数据**；seed 只覆盖已知 id，从不修正该实时拉取模型。

**修复**（根因点 + 存量修复，surgical）：
1. **根因点修复**：改造 `schema_for_enabled_operations`——以 `default_operation_schema` 为基底，合并历史字段，**强制保证每个操作条目带合法的 `parameters` 对象**（缺则补 `{}`）。这是 `validate_schema_for_operations` 与 `replace_provider_model_bindings` 共用的唯一汇聚点，修复即同时解决「校验通过」与「保存时 DB 自愈」。
   - 关键决策：`resultType` 由操作键本身决定，**不**在 repair 中静默覆盖（否则会削弱既有测试 `enabled_schema_keeps_only_one_generation_category` 对「类别错配应被拒」的校验；真实畸形数据 resultType 本就正确）。
2. **存量数据迁移**：`Storage::open` 新增 `repair_malformed_model_definitions()`（storage.rs），对每条 `model_definitions` 用 `operations_from_schema` 取操作列表、`schema_for_enabled_operations` 重算，shape 变化才 UPDATE；并 DELETE 形如 `remote::{model}`（缺 provider 段）且无绑定引用的孤儿行。幂等，每次启动执行。

**验证**：
- Rust 44 测试全绿（含 2 新增：`malformed_operation_schema_is_repaired_with_parameters`、`malformed_operation_schema_is_repaired_on_open`；既有 `enabled_schema_keeps_only_one_generation_category` 仍通过）。
- fmt clean、clippy `-D warnings` 零警告；前端 typecheck + vitest 62 全绿。
- **DB 实证（非破坏）**：复制用户实时库到临时目录，用临时 env 守护测试跑真实 `Storage::open` 触发迁移——`remote::provider-…::doubao-seedance-2.5` 被修复为完整合法 schema（各操作均带 `parameters` 对象 + `requestProfileId`/`request`），孤儿 `remote::doubao-seedance-2.5` 计数归 0。验证后删除临时库与临时测试。
- 结论：用户**下次启动应用（rebuild + relaunch）时自动自愈**，无需手动改库；修复后保存不再报该错。

**经验**：
- 「保存模型」链路存在多道校验门，前一道失败会**遮蔽**后一道的真实问题——排查时要逐道剥离，不能只修第一道就认为结束（Bug 2 正是 Bug 1 修好后暴露的下游）。
- 操作 schema 的硬约束：`parameters` 必须是对象、`resultType` 须与操作键一致；任何落库/透传点都要保证，否则用 `schema_for_enabled_operations` 兜底修复。
- 对「实时拉取的模型」与「seed 已知 id 模型」要区分：seed 迁移只覆盖已知 id，实时拉取模型的畸形数据只能靠 `repair_malformed_model_definitions` 这类全表修复迁移兜底。

## 修复：对象存储连通性测试 HTTP 403 SignatureDoesNotMatch（Bug 3，TOS 预签名）

**现象**：供应商设置里保存 TOS 直连配置后自动连通性测试失败，TOS 返回 `SignatureDoesNotMatch`（AK 合法被原样回显 `AccessKeyId: AKLT…`）。用户坚称配置正确、是程序问题。

**诊断关键**：
1. `tos_sign.rs::presign_url` 的 V4 签名算法用 Python 独立复算，与官方文档向量 `353aa555…` **字节级一致** → 签名数学正确，不是算法 bug。
2. 前端 `TosStagingSettings.tsx` 把 `endpoint` 锁死为裸主机 `tos-cn-beijing.volces.com`、`region=cn-beijing`；`validate_tos_config` 已强制 endpoint 为无 scheme/无路径的裸 host → `host={bucket}.tos-cn-beijing.volces.com` 正确。
3. 因此签名可变因子里唯一会被 TOS 以不同值重算的只有 `host` 头域 → 只有「请求实际到达的 Host ≠ 签名时 Host」才会触发该错，而 Host 变化只能源于**重定向**。
4. `StagingService` 此前复用 `ProviderRuntime` 共享 reqwest 客户端，其默认 `redirect::Policy::limited(10)` 会**自动跟随 TOS 的 301/307 重定向到规范化 Host**，把同一套签名查询串重放到不同 Host → TOS 用新 Host 重算签名即报 `SignatureDoesNotMatch`。呼应火山引擎公告《桶域名或预签名的 URL 访问限制变更》(2116752)。

**修复**（surgical，程序侧）：
1. `staging.rs` 新增 `build_presign_http_client()`：专用 reqwest 客户端，`redirect::Policy::none()`（其余超时/UA 与共享客户端一致）。`StagingService::new` 改用它（改返回 `BackendResult<Self>`，mod.rs 调用点加 `?`）。所有预签名 GET/PUT/DELETE 均走此客户端，不再跟随重定向。
2. `ProbeVerdict` 新增 `Redirected`，`classify_probe_response` 把 3xx 归因为 `redirected`（原 302→HttpError 的既有测试已同步更新）；前端 `backend.ts::describeConnectivityTest` 新增 `redirected` 提示「请求被重定向，请确认 Endpoint/地域/桶名与控制台一致」。
3. 设计文档 `docs/integrations/tos-staging-design.md` 新增「预签名请求与重定向约束」一节固化该约定。

**验证**：Rust 5 staging 测试（含新增 `presign_client_does_not_follow_redirects`——本地 307→捕获服务器，断言客户端直接返回 307 且捕获服务器从未被访问）；前端 62 vitest 全绿、typecheck OK、eslint `-max-warnings 0` 零警告、cargo fmt clean、cargo clippy `-D warnings` 零警告。

**经验**：预签名 URL 签名绑定 Host，任何自动跟随重定向的 HTTP 客户端都会破坏签名 → 预签名请求必须 `redirect::Policy::none()` 并显式处理 3xx。签名算法经官方向量验证无误后，403 SignatureDoesNotMatch 几乎总是指向「Host 在传输中被改变（重定向）」，而非密钥本身。

## Bug 3 续（Round 2）：重定向修复后仍 403 → 真正的根因是前端 SecretKey 未 trim

**关键反转**：用户用 `pnpm tauri dev` 重新编译 Rust（重定向修复已生效）后，**仍**返回 403 SignatureDoesNotMatch（不是新的 `redirected` 提示）→ 证明纯重定向假设被证伪：是「同一 Host 下的直接签名不匹配」，Host 没变。

**真正的根因**（前端 trim 不对称）：
- `TosStagingSettings.tsx` 的 `handleSave` 里：`accessKey` 做了 `.trim()`，但 `secretKey` **没有**（`const secretKey = secretKeyRef.current?.value ?? ""`）。
- 火山引擎控制台复制的 AK/SK 常带结尾换行/空格；SK 一旦带尾随空白被原样 `JSON.stringify` 存入系统凭据管理器，本地 HMAC 就用「带空白的错误 SK」计算签名 → 正好 `SignatureDoesNotMatch`（AK 因被 trim 能正常回显，更凸显是 SK 出错）。这与用户「我配置正确」并不矛盾——他粘贴的内容肉眼对，但多了一个看不见的换行符。

**修复**（两层归一化，surgical）：
1. **Rust 端 `tos_sign.rs::TosCredentials::parse`**：对 `access_key` 与 `secret_key` 都 `.trim()`，并用 trim 后值判空。这样**已存储的脏凭据在载入时自动归一化**，无需用户重新录入；与官方 SDK 行为一致。新增回归测试 `credential_secret_is_trimmed`（含首尾空白 + 纯空白判空拒绝）。
2. **前端 `TosStagingSettings.tsx`**：`secretKey` 补 `.trim()`，从源头杜绝脏密钥写入凭据管理器。

**验证（本轮）**：Rust `backend::staging` 5/5 + `backend::tos_sign` 6/6（含 `credential_secret_is_trimmed`）全绿；`cargo fmt --check` clean；前端 `typecheck` + `lint(--max-warnings 0)` 全绿。注意：`pnpm test` 全量跑时 `src/App.canvas.test.tsx:361` 偶发失败（期待 `.canvas-asset-node` 数量 +1 得 0），**但该文件单独运行 18/18 全过** → 是跨测试环境污染的已有 flaky，与本次 TOS 改动无关（改动仅限 staging/签名/设置表单，且 typecheck/lint 均未报导入或类型错误）。

**结论**：用户**重新编译并重新保存凭据**后，连通性测试应通过（即便不重填，Rust 端 trim 也会自愈已存的脏 SK）。若仍 403，则进入「诊断日志」分支：在 `test_connectivity` 打印本地算出的 `host` 与完整 `StringToSign`（重点是 scope 的 `date/region/service`），与 TOS 回显逐段比对，排查 region/endpoint 是否真与控制台一致。

**经验**：「AK 被原样回显 + 签名不匹配」这一特征组合，在排除 Host/重定向后，**优先怀疑 SK 文本含不可见字符（换行/空格/全角）**，而非算法或 region 错误。前端所有密钥录入点都应 `.trim()`，且后端解析时应做二次归一化兜底（前端不可信）。

## Bug 5：对象存储连通性测试误报「桶不存在」（HTTP 404 NoSuchKey 被错误归类）

**现象**：Bug 3 的 403 修复（重定向 + SecretKey trim）生效后，连通性测试不再 403，但转为失败提示「HTTP 404：桶不存在，请检查桶名和地域」，错误体为 `{"Code":"NoSuchKey",...}`。用户猜测是「桶名里带隐藏空格」。

**诊断（排除桶名空格假设）**：
- TOS 的鉴权与解析顺序是 **先验证签名 → 再解析 bucket → 再检查 object key**。
- `NoSuchKey` 指「object key `staging/.connectivity-probe` 不存在」，它**只会在 bucket 已被成功解析后**才返回；若桶名真有隐藏空格，TOS 会返回 `NoSuchBucket`（或解析不到桶），**绝不会**返回 `NoSuchKey`。
- 故「桶名带隐藏空格」假设不成立；用户的配置（Region `cn-beijing`、Endpoint `tos-cn-beijing.volces.com`）正确。
- 真正的根因：探针用的是 GET 一个**从未被创建**的对象 `staging/.connectivity-probe`，404+NoSuchKey 正是「连通/凭据/桶都有效」的健康信号（`ProbeVerdict::Ok`）。但 `classify_probe_response` 把 `404 => ProbeVerdict::BucketMissing`（桶不存在）作为兜底分支，依赖 `extract_error_code(body)` 读出的 `Code` 来特判 NoSuchKey。

**根因（JSON 错误体未解析）**：
- `extract_error_code` 旧实现**只**解析 XML `<Error><Code>...</Code></Error>`。
- 火山引擎 TOS 在**部分错误响应中返回 JSON 形态** `{"Code":"NoSuchKey","Key":"...","Message":"..."}`（用户日志正是此形态）。
- 旧代码对 JSON 的 `serde_json` 解析失败 → 返回 `None` → 落入 `404 => BucketMissing` → 误报「桶不存在」。
- 即：**不是桶的问题，是错误体解析器漏读了 JSON 形态**。

**修复**（surgical，解析层）：
- `staging.rs::extract_error_code` 改为**先尝试 JSON**（`serde_json::from_str::<Value>`，取 `Code` 字段并 trim），失败时回退到原 XML `<Code>` 解析。两种形态均覆盖。
- 测试 `extract_error_code_handles_xml_shapes` 新增两组 JSON 用例（`{"Code":"NoSuchKey",...}`、`{ "Code" : "NoSuchBucket" }`）；`probe_verdict_classifies_tos_responses` 新增「404 + JSON NoSuchKey → ProbeVerdict::Ok」断言。

**验证（本轮回合）**：`cargo test --lib backend::staging` 5/5（含新增 JSON 用例）；`cargo fmt --check` 初报测试行过长 → `cargo fmt` 自动折行后 clean；`cargo clippy --locked --all-targets -- -D warnings` 零警告；完整 `cargo test --lib` 46/46 全绿，无连带回归。

**结论**：用户**重新编译（`pnpm tauri dev`）后**连通性测试应通过（404+NoSuchKey 现被正确判为「连通」）。桶名无隐藏空格；之前 403→现 404 的转变恰恰证明签名/trim/重定向三类修复均已生效。

**经验**：
- TOS 错误响应**可能同时是 XML 或 JSON** 两种形态，任何解析 `Code` 的逻辑都必须同时兼容两类，否则会在 JSON 形态下漏读 → 误判。
- 区分两类 404：`NoSuchKey`（对象不存在，连通健康）vs `NoSuchBucket`（桶不存在，配置错误）。前者出现**必然先于**桶解析成功，可直接作为「凭据+桶有效」的判据，反向排除「桶名含隐藏空格」。
- 把「错误体疑似脏配置」的猜测，先用「服务鉴权/解析顺序」这一硬事实反证，再定位到解析逻辑缺陷 —— 比直接 accept 用户假设更省力且更准确。

### Bug 6 第三轮（终极根因）：云端脏数据 + React duplicate key reconciliation 串台

**纠正上一轮判断**：之前的"重启 dev server"虽有必要，但**不是真正的 root cause**。用户重启后仍报 bug，并附 React duplicate key 警告——这才是真因。

**用户实拍证据**（重启 + 清 Vite 缓存后）：
- Console 出现大量 React 警告：`Encountered two children with the same key, asset-20260716091740-52j2s`、`...52j2s`、`...5dgnf`、`...jvzrr`、`...64qd7`、`...fjp84` 等，每个 ID 重复 6-7 次；
- 视频 tab 仍渲染 8 个以上 qpm-N（Image）卡片。

**云端脏数据实测**（真打 `https://47.94.250.161/v1/assets/list`）：
- 100 个素材对象，**仅 31 个唯一 ID**；
- 5 个 ID 各重复 14-15 次，同一 `asset-20260716091740-52j2s` 对应 `qpm-12 / qpm-7 / qpm-2 / full-10 / stab-19` 等 15 个不同 name 的素材对象；
- 5 个重复 ID 全部 `asset_type: Image`，看起来是后端 join / 分页去重缺失的脏数据。

**根因链（终极）**：
1. 云端 API 返回 100 个对象，仅 31 个唯一 ID；
2. 前端 `parseCloudAsset` 不去重，全部接受 → `cloudAssets` 100 个对象、31 个 ID；
3. `cloudAssetToItem` 保留 `asset.id` → `libraryAssets` 100 个 `AssetItem`、31 个 ID；
4. 渲染 `visibleAssets` 用 `key={asset.id}`，React 检测到大量重复 key，发出「Encountered two children with the same key」警告；
5. **React 在 duplicate key 下的 reconciliation 行为未定义**——它会保留所有重复 key 对应的 DOM 节点不去重；切 tab 时 React 试图清理旧节点但因 key 冲突没法精准定位，部分 image 卡片 DOM 残留在 video tab 的 grid 里；
6. 用户看到 video tab 里渲染了 image 卡片（实际是 React 残留 DOM + video tab 真正渲染的 video 卡片叠加）。

**修复（前端防御性去重）** —— `src/lib/backend.ts::parseCloudAssetPage`：
- 用 `Set<string>` 按 id 去重，**保留首次出现**（首次胜出更稳定，避免同一个素材对象在去重后跳变）；
- 注释里说明云端脏数据的事实 + React duplicate key 风险，给未来维护者留线索。

**单元测试** —— `src/lib/backend.test.ts` 新增 it `"云端返回重复 id 的素材对象时按首次出现去重"`：

   - `closeClearCanvasDialog`：优先 `dialog.close()`，fallback 到 `removeAttribute("open")`；
   - `confirmClearCanvas`：先 `clearCanvas()` 再 `closeClearCanvasDialog()`。

2. **Dialog JSX**（放在 `<main>` 内部 `</main>` 前）：
   ```jsx
   <dialog ref={clearCanvasDialogRef} className="confirm-dialog"
     aria-labelledby="clear-canvas-dialog-title"
     aria-describedby="clear-canvas-dialog-desc">
     <form method="dialog" className="confirm-dialog__form"
       onSubmit={(event) => event.preventDefault()}>
       <h2 id="clear-canvas-dialog-title">确认清空画布？</h2>
       <p>将移除画布上所有节点与连线。<strong>任务历史保留</strong>（用于复现与审计）。此操作不可撤销。</p>
       <div className="confirm-dialog__actions">
         <button type="button" onClick={closeClearCanvasDialog}>取消</button>
         <button type="button" className="...--danger" onClick={confirmClearCanvas}>确认清空</button>
       </div>
     </form>
   </dialog>
   ```
   - `<form method="dialog">` 让 ESC / Enter 自动触发 submit（由 `onSubmit` preventDefault 接管，避免浏览器默认 close() 抢先）；
   - `aria-labelledby` / `aria-describedby` 让 screen reader 与 testing-library 都能按 name 找到 dialog。

**经验（叠加上一轮）**：
- **破坏性操作的二次确认，原生 `<dialog>` + `showModal()` 是首选**：ESC 关闭、focus trap、::backdrop 遮罩、form 集成全部免费提供，比自建 modal 框架轻得多；
- **jsdom 不支持 `HTMLDialogElement.showModal()`（jsdom 30 已知限制）**，必须在代码里加 feature detect fallback（`typeof dialog.showModal === "function"` + try/catch + 手动 setAttribute("open")），否则测试跑不起来；
- **测试用 queryByRole("dialog")**：dialog 元素 + `aria-labelledby` 指向 title 时，testing-library 能正确按 name 找到 dialog；但 dialog 必须有 `open` 属性（modal 或手动设置），否则 role 不是 dialog；
- **dead code 必须清**：上一轮的 `clearConfirming` state、timer ref、`is-confirming` CSS、unmount cleanup effect 全部删除，避免历史代码堆积；
- **surgical 修复原则**：用户给了明确方向（"弹窗确认"），立刻推翻自己上一轮的设计而非叠加妥协——保留内联确认 + 加 modal 会变成「两种确认机制并存」的混乱。
