# drama-auto-pipeline · 单文件版（standalone）

> **版本 V2.3** ｜ 铁律 **95 条** ｜ 不变式 **658 条** ｜ 对抗测试 **13 个** ｜ 审核关 **7 道** ｜ 发版门禁 **4 道**
> 
> **一份文件读完全流程。** 无需安装、无外部依赖，可直接把本文件喂给任意 AI 当操作手册。
> 安装包与完整实现见同目录 `drama-auto-pipeline-V<版本>.zip`。

> ⚙ 本文件的数字与铁律清单**由 `tools/make_deliverables.py` 从 `VERSION` / `SKILL.md` / `tools/checks.txt` 自动生成**，发版时刷新 —— 手抄一定会漂。

## 0 · 这是什么

把**一部小说或一个创意**，变成**一部能交付的短剧成片**的全自动流水线。

它不是「生成几个片段」：整条链路有 7 道审核关卡，每一关都停下来让用户审；
每一段视频都带上同一套参考素材（角色图 / 场景图 / 上一段尾帧 / 角色音色）；
所有改动都要过 4 道发版门禁才能发出去。

```
小说/创意 + 主角图
   ↓
关1 剧本 → 关2 风格 → 关3 资产 → 关4 分镜 → 关5 提示词 → 批量生成 → 关6 视频 → 拼接 → 关7 成片
   ↓            （每关一个 HTML 审核页，可改、可导出 diff、可退回）
交付四件套（成片 + 全链总览 + 资产包 + 成本台账）
```

## 3 · 常用命令（照抄可用）

```bash
# 环境自检
python tools/doctor.py

# 关 4 · 分镜机检（0 硬错误才允许冻结）
python references/check_storyboard.py --project-root "<项目根>"

# 冻结分镜方案（双条件事务：机检 0 错 + 人工已批）
python references/approve_storyboard.py --project-root "<项目根>" --by 用户 --note "关 4 通过"
python references/approve_storyboard.py --project-root "<项目根>" --revoke --reason "规则变严/方案改过"

# 阶段六 + 关 5 · 生成提示词与审核页（纯本地零算力）
python references/batch_run_drama.py --project-root "<项目根>" \
  --storyboard "<项目根>/分镜脚本/storyboard.json" \
  --aspect "16:9 (Widescreen)" --dump-prompts

# 关 5 · 标记通过（必须同时确认分辨率；确认值要写真实数字）
python references/batch_run_drama.py --project-root "<项目根>" \
  --storyboard "<项目根>/分镜脚本/storyboard.json" \
  --aspect "16:9 (Widescreen)" --approve-prompts \
  --confirmed-resolution "16:9 · 一采 0.7 MP · 二采 ×1.5 · 推算输出 1680×960｜交付不标 1080P"

# 阶段八/九 · 批量生成（**默认多参**；首镜试产用 --only；双通道并行按需）
python references/batch_run_drama.py --project-root "<项目根>" \
  --storyboard "<项目根>/分镜脚本/storyboard.json" \
  --aspect "16:9 (Widescreen)" --only 3,4,5 --workers 5
  # 纯文生视频（明确的例外，一致性无锚点）才加 --noref
  # 企业级通道按秒扣真实钱包：不用就加 --no-enterprise

# 审核页导出合并（用户在页面上改完，点导出得到 seg_N_edit.json）
python references/apply_seg_edit.py --project-root "<项目根>" --edit <seg_N_edit.json>
python references/apply_seg_edit.py --project-root "<项目根>" --sync-derived   # 重算顶层派生字段

# 重建任意一关的审核页
python references/audit_html_builder.py --project-root "<项目根>" --stage storyboard|prompt|video|final

# 逐段一致性审核
python references/consistency_auditor.py --shot-dir "<项目根>/视频/shot_03_xxx" --project-root "<项目根>"

# 发版四道门禁（任一不过 → 拒绝发版、不写快照、不打 tag）
python tools/snapshot.py --check-only
python tools/snapshot.py --version 2.3 --kind minor --project "《片名》" --summary "…" \
  --item "…" --verify "…"

# 回退到任意历史版本
python tools/rollback.py --list
python tools/rollback.py --to V2.3

# 刷新交付物（发版流程会自动调用；也可手动跑）
python tools/make_deliverables.py
```

## 5 · 通用判据（跨项目可复用，值得抄到别处）

> 这些不是「本 skill 的规矩」，是「凡是做 AI 生成流水线都该守的」。每条都来自真实事故。

**1. 改动落在「能被读回文件验证」的链路上，就必须有读回文件的断言**
　　「命令没报错」不等于「文件写对了」；--dry-run 输出正确也 ≠ 文件正确。

**2. 同一条规则在 A 处是建议、在 B 处是门禁 —— 这是必然的返工源**
　　下游是硬门禁的约束，上游不许降级成软提示；发现两处判同一件事，先问「哪一处更严」，把更严的提上去。

**3. 凡是「自动生成的描述句」，都要有一条断言盯着它「说的是不是真的」**
　　这类缺陷不崩、不报错，只让模型收到错误或自相矛盾的指令 —— 它是静的。

**4. 「谁说了算」要在代码里明确一次**
　　运行时参数 > 文件静态值；显式参数 > 默认值；源数据 > 识别结果。

**5. 默认值就是产品决策，别让它是个历史遗留**
　　默认必须是「一致的那条路」；会伤一致性的模式只能显式进入，且必须大声警告。

**6. 「命令跑成功了」与「东西做对了」是两件事**
　　前者是退出码，后者要靠独立证据。汇总行只说明「提交了 N 次」，不说明「提交对了」。

**7. 凡是「文档说了什么」与「代码做了什么」不一致的地方，先按最贵的那个方向去想**
　　文案歧义在别处只是难看，在花钱的地方是账单。

**8. 门禁是代码，就有 bug；bug 分两种，必须分清**
　　「真的拦住了坏东西」和「门禁自己坏了」。后者的特征是「一切正常时也报错」，所以每道门禁都要有「正常输入必须放行」的基线断言。

**9. 同一套业务枚举只能有一份定义，其余一律派生**
　　四份定义里的三份一致，说明不了任何问题。

**10. 识别失败 ≠ 不存在**
　　「有没有」必须问源数据，不能问「我识别到了几个」—— 后者会把「我没看懂」误报成「本来就没有」，而豁免逻辑会自动把错误洗白。

**11. 派生值只能有一个产出点，而且那个产出点必须是代码**
　　同一个值有两份实现，合并时「后写的覆盖先写的」，源头反而说了不算；必然会错的字段就该由代码维护。

**12. 能反推的都不要反推；作者才知道的事实必须显式声明**
　　关键词只能当提示不能当判据 —— 一个词出现在多种语境里，就不能单拿它当判据。

**13. 会被机器比对的字符串，必须格式化到「语义等价即字符串相等」**
　　浮点误差、对象 repr、内存地址、时间戳一个都不许混进去，否则「同一个值」会被判成两个。

**14. 缓存必须跟着源数据一起失效**
　　「文件在就复用」不是缓存策略，是忘了失效 —— 源数据换了下游还在用旧的，而且完全静默。

**15. 启动预检要比「提交」更早**
　　能不花钱就失败的事，绝不等到第一步提交时才炸。

**16. 拿不准时选「更贵但更稳」的那条**
　　多参只多一次上传、几乎不加钱，却是一致性的唯一抓手；省下的那点成本会以「整批重做」的形式还回来。

## 6 · 四个最容易踩的坑（血泪版）

### ① 默认值悄悄关掉了「一致性」

```
整批 20 段提交时：noref=true · ref_count=0 · audio_count=0
→ 用户自带的角色图没用上、尾帧锚点没生效、音色没上传
→ 同一角色逐段换脸换发型 → 20 段全废 + 3259 币
```

根因：默认值把「多参」关了，而它引用的工作流文件本来就是多参版本 —— **默认值与它指向的资源互相矛盾**。
规矩：**默认必须是「一致的那条路」；会伤一致性的模式只能显式进入，且必须大声警告。**

### ② 报「20/20 成功」，而出片不可交付

汇总行是程序自己打的 —— 它会诚实地报告「我提交了 20 次」，**但不会告诉你「我提交错了」**。
规矩：**批量跑完必须抽检产出物**：① 逐段提交记录里的素材计数 ② 抽帧触点图肉眼过 ③ 与参考素材对照。

### ③ 同一套枚举写了四份，唯独最要紧的那份漂了

```
四处都定义「哪些 beat type 算台词」：三处含 "line"，唯独生成提示词那份漏了
→ 全片台词被当动作输出 → 人物不会说话
→ 校验器因缺标记整块跳过 → 「0 错误 0 警告」= 假安全
→ 机检把「识别失败」当成「本来就没有」→ 直接豁免（19/19 全绿）
```

规矩：**同一套业务枚举只能有一份定义**；**识别失败 ≠ 不存在**。

### ④ 门禁自己也会坏，而且坏起来会「一切正常时也报错」

- 覆盖范围：被改的那张页面**没被冒烟覆盖**（夹具里没它的数据 → 每次「数据不足」跳过）
- 唯一实现：门禁脚本**又实现了一遍**同一检查，返回值一改就静默错位，报出「看起来很严重的假消息」
- 命名极性：`failed` 写成 `ok` → **全绿时也拒绝发版**

规矩：冒烟要覆盖「会被改到的产物」；同一条逻辑只能有一处实现；布尔值的名字必须和它的极性一致；
**每道门禁都要有一条「正常输入必须放行」的基线断言。**
