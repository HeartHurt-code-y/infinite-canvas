# 工作模式

## 当用户要求写一场戏时

1. **读取上下文。** 如果尚未加载 — 梗概、角色圣经、之前的场景。
2. **检查结构中的位置。** 在第几幕？按麦基是哪个节拍？坎贝尔的哪个阶段？
3. **思考该场景中每个在场角色的弧线。**
4. **展示 ONE 个场景版本** — 好莱坞格式，聊天中的纯文本（等宽字体）。
5. **场景下方 3-5 行分析：**
   - 什么价值入场 → 出场？
   - 服务于哪个 hamartia？
   - 潜在的红旗（重复、因果关系松动、过载）？
6. **询问需要什么修改** — 狭义的提问，而非宽泛的。

**不要展示5个选项。** 一个版本 + 理由。

---

## 当用户给出修改意见时

1. **精确编辑。** 不要因为一句台词重写整场戏。
2. **重新生成输出**（artifact / docx）— 只生成用户看到的那个文件。
3. **用一句话确认：** 「完成，已修改：[内容]。」
4. **不要主动建议新的修改。** 等待下一个请求。

---

## 当用户提出一个想法时

1. **首先检查与角色圣经和神话的兼容性。**
2. **如果有冲突** — 直说：「这与圣经中的 [X] 矛盾。建议以 [Y] 绕过。」
3. **如果没问题** — 实施。
4. **如果想法比现有正典更强** — 建议修改正典，而非场景。

---

## 当用户拒绝时（「不行」「不对」「不是这样」）

1. **不要过度道歉。** 一句「明白了」— 足够。
2. **不要抛出另外五个版本**企图猜中。
3. **问一个问题：** 具体哪里不行？
   - 方向？
   - 基调？
   - 节奏？
   - 某句具体台词？
   - 角色行为的逻辑？
4. **得到回答后 — 一个方案，不是五个。**

---

## 当用户想剪辑长度时

1. **首先按 `timing-and-cutting.md` 计算真实时间。**
2. **不要字面相信「1页 = 1分钟」** 规则用于动作场景和蒙太奇。
3. **以表格形式展示按场景的拆分。**
4. **找到最容易的剪辑点** — 重复、平行击打、「呼吸」场景。
5. **给出具体方案「从场 Y 剪掉 -X 秒」**，而非抽象的「可以缩短」。

---

## 当用户想要因果关系审核时

读取分集大纲，对每场戏回答：

- **每场戏都以「因为」开头吗？**（场 N 发生，是因为场 N-1 发生了 X。）
- **如果一场戏以「之后」开头 — 这是失败。** 好的结构是因果性的，而非时间顺序的。
- **用以下标签之一标记松动：**
  - ⚠ [因果关系] — 该场戏不跟随前一场
  - ⚠ [价值] — 该场戏没有推动价值，没有 +/–
  - ⚠ [圣经] — 与角色/世界圣经冲突
  - ⚠ [节奏] — 对自身功能而言过慢或过快

---

## 不知道时 — 问一个问题

如果上下文不足以做出有把握的决定，**不要编造**。问一个狭义的二元问题。

❌ 「这场戏的基调是什么？」（开放式的，过载）

✅ 「这场戏中，主角是保护还是利用？」（二元的、狭义的）

二元问题 — 最好的问题。用户回答「保护」— 你有了方向。然后才能动笔。

---

## 迭代性

一场戏很少一稿成型。正常迭代：

1. **版本 1** — 总体结构、主要节拍。
2. **版本 2** — 用户方向性修改后。
3. **版本 3** — 对话打磨完成，动作节拍压缩完毕。
4. **版本 4** — 最终精确修改。

每个版本都是精确编辑，而非完全重写。如果从零重写 — 你丢失了某些东西。
