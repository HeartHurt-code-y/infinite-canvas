# 音乐 MV 自动生成 SOP V1.0（mv-auto-pipeline）

> **当前精确版本：以本目录 `VERSION` 文件为唯一权威**（发版/回退见 `CHANGELOG.md` 与 `tools/`）。
> 标题行与 frontmatter 只写**主版本号**（minor 时才动）；精确版本一律以 `VERSION` 为准。
> ⚠️ **正文里不再重复写精确版本号** —— 同一个版本号写两遍就是漂移源
> （drama-auto-pipeline 出过「VERSION=1.5 但正文还停在 V1.3」的事故，见其 CHANGELOG）。
>
> **本 skill 与 `drama-auto-pipeline` 的关系**：同构但**不同源**。
> 流程骨架、审核关制度、进化/回退机制（铁律 F）、project_provider 客户端口径共享同一套经验；
> 但**时间基准、发声类型、口型规则、工作流**这四件事完全不同 ——
> 短剧是「剧本驱动」，MV 是**歌曲线驱动**。千万不要把短剧的段长设计逻辑套到 MV 上。

## 一句话需求 → 交付物

> 「给一首歌和一张图，出来一个完整的、完美的音乐 MV。」

| 输入 | 必需 | 说明 |
|---|---|---|
| **歌曲文件** | ✅ 必须 | mp3 / wav / flac / m4a，放 `音乐/`；没有歌就没有 MV，这一项不接受「推断」 |
| **官方歌词**（文本） | ⚠️ 强烈建议 | 没有也能跑（只用 ASR），但 ASR 必然有错字，交付前必须逐行核 |
| **主人公图** | ⭕ 可选 | 给了 → 走 Ref2VA 多参模式（主角跨段一致）；不给 → **必须问一句**「要不要帮你生成一个主人公」；用户说不要 → **无主角音乐 MV**（全程无固定面孔、全员不对口型） |
| 风格参考图 / 判据 | ⭕ 可选 | 给了就直接反推风格，跳过三选一推荐但仍需用户确认 |

| 交付物 | 回答什么问题 |
|---|---|
| `视频/final/final_master.mp4` | **成片（交付首选）** = 画面轨 + 原曲母带重贴，绝对对齐 |
| `视频/final/final.mp4` | 逐段内嵌音乐版（各段自带音乐直接拼，可交叉验证对齐） |
| `视频/final/对齐验收.html` | **口型-画面-音乐对齐有没有做到**（逐段滞后量 + 波形相关度 + 能量） |
| `分镜脚本/分镜表.md` | 怎么做的（逐段窗口/口型/景别/画面构想） |
| `歌词/lyrics.lrc` + `歌词/lyrics.json` | 歌曲线是什么（权威时间轴） |
| `审核/01..08 + 全链总览.html` | 8 道关逐段细审 + 整条链怎么走的 + 花了多少 |

## 🔒 不可变铁律

**以下规则不可在后续版本中修改或弱化，除非用户明确说"改"。**

### 铁律 A · 音乐基准与歌词（MV 特有）

**A1. 音乐是唯一时间基准。**
- 段长、切点、口型位置**全部**从 `歌词/lyrics.json` 的时刻推导。
- ❌ 禁止凭空设计段长；❌ 禁止「先想好画面再去找音乐位置」。
- 判据：任何一段的 `music_window` 必须能在 `lyrics.json` 里指出来源。

**A2. 歌词时间轴必须完整提取，而且必须逐行核对。**
- 歌词**一行不能少**（含重复段、和声行、桥段）；时间轴**必须落盘**：
  `歌词/lyrics.json`（权威，逐行 + 对齐置信度）+ `歌词/lyrics.lrc`（人读 / 外部工具用）。
- **ASR 只提供时间，文本必须用官方歌词校正**（铁律 A3）。ASR 的同音字错误率在歌曲上很高
  ——「海啸 → 海上」「循环 → 生还」这类错误必须靠官方歌词纠正。
- 对齐命中率低于阈值（默认 55%）的行标 `review_needed`，**必须人工听一遍再定稿**；
  **禁止静默放过** —— 一行错位会让整段口型全错。

**A3. 强制对齐优先，三条取值路径按优先级**
1. **官方歌词 + ASR** → `align_lyrics.py --asr ... --official ...`（推荐：文本准 + 时间准）
2. **现成 LRC** → `align_lyrics.py --lrc ...`（直接解析 + 自检；改时间最方便）
3. **只有 ASR** → 全部行标 `review_needed`，必须人工过一遍
- 对齐算法是字符级 **Needleman-Wunsch 全局对齐**（纯标准库，不依赖 numpy）：
  两侧去标点后逐字做 DP，把官方歌词行映射到 ASR 的字符时间上。

**A4. 时间轴必须过连续性自检（`align_lyrics.py` 自动跑）**
- 行起止**单调递增、行间不重叠、无 >2s 无标记空档**；
- 空档必须**显式**插 `[instrumental]`（间奏不是bug，但必须被标出来，因为它决定了分镜切点）；
- 语速体检：中文 > 9 字/秒 视为时间轴错位的嫌疑。
- 任一不过 → 关 1 不放行。

**A5. 音乐窗口必须连续无缝、Σ = 全曲长、且不许手算**
- 段 i 的窗口 = `[t_i, t_{i+1})`，且 `t_{i+1}` 就是段 i+1 的起点 —— **无缝、不重叠**。
- `Σ 窗口 = 全曲长`（末段窗口收到歌曲终点，标记 `tail: true`）。
- 窗口由 `plan_mv_storyboard.py` 统一产出、写入 `storyboard.json`，
  **由 `check_alignment.py --plan` 复核**（关 6）。**任何环节不得手写窗口秒数。**
- 切点**只落在歌词行尾**：宁可某段略微超长，也不把一句歌词切成两半。

**A6. 歌曲文件原样保留。**
- 用户给的原始音频**不许覆盖、不许重编码**（`音乐/song.mp3` 只读）。
- 需要 16k wav 给 ASR、需要切窗给工作流，一律写到 `音乐/song_16k.wav`、`音乐/cuts/`。

### 铁律 B · 口型策略（MV 特有，用户明确要求）

**B1. 只有中近景才设计对口型。**
- 允许对口型的景别（白名单，只有这四类）：
  `ECU 大特写` / `CU 特写` / `MCU 近景` / `MS 中景`。
- ❌ **禁止**在 `MLS 中远景` / `LS 全景` / `WS 远景` / `EMPTY 空镜` / 背影 / 群像 上设计对口型。
- 机检硬约束：`sing_mode=sync` 的段，`shot_size` 必须落在白名单里，否则关 4 / 关 6 拦下。

**B2. 不是每句都对口型。**
- 对口型段占比目标 **45%**（可调 `--sync-ratio`），建议区间 **35%~60%**。
- 连续对口型段 **≤3**，中间强制插叙事镜 / 空镜 / 群像（否则观众审美疲劳，也更容易看出穿帮）。
- 其余画面由这些承载：叙事镜（人物不对口型地生活）、环境空镜、群像、道具特写、意境镜头。
- 抽样要**均匀撒在全曲**（脚本按位置等距抽样），不许把对口型全挤在开头或副歌。

**B3. 对口型段只唱完整的歌词行。**
- 一段只包含**完整的**歌词行（行首到行尾都在这段窗口里）。
- 确需让一句歌词跨段延续 → 显式用官方 `<scenetrans>` + 连续性短语，并在 `summary` 声明
  「台词不要求与本镜画面同步收尾，不加快、不吞字」（项目视频模型 铁律 R37）。

**B4. 不对口型段的硬约束（这是最容易翻车的地方）。**
- 正文**严禁**出现 `sings:` / `says:` / `shout together,` —— 一旦出现，项目视频模型 会让人物跟着唱。
- 必须写 `NO_SYNC_DECL`（脚本自动注入）：
  > 本段人物**不对口型**：嘴唇保持自然闭合，或只做与歌词无关的日常动作（呼吸、吞咽、微笑、说话前吸气），不得跟随音乐人声开合。
- `Negative` 必须含 `no lip sync, no mouthing lyrics, no extra vocals`（脚本自动注入）。

**B5. 对口型段必须声明「口型严格跟随音乐母带」。**
- `summary` 写：本段人物**跟随音乐母带对口型演唱**，口型必须与音乐人声严格同步，
  每一句歌词的起止都与母带人声一致。
- 验收（关 8）：该段音频必须有非空人声能量，且与母带同位置波形相关度达标。

### 铁律 C · 分镜与提示词

**C1. 段长 ∈ [4,15] 秒，并按 17 帧网格对齐。**
- 请求时长 = `align(窗口长)`，公式 `max(5, round(a*24)) + (5 - (max(5, round(a*24)) % 17)) % 17`
  → `12s → 12.25s`、`6s → 6.58s`。
- 因为公式有 `max(5, …)` 下限，**4~5s 的窗口会被请求成 5s，成片再裁回窗口长度** —— 这是正常的。
- ⚠️ 该公式来自 drama W-A 的实测，**MV 工作流是否同样对齐必须实测确认**
  （跑一次 12s，ffprobe 看真实帧数），确认后把 `align_formula_confirmed` 改成 true。

**C2. 是唱歌，不是说台词 —— 提示词口径（用户明确要求）。**
- 发声行一律走**官方英文框架**（项目视频模型-ref2va-optimizer 铁律 35，官方 `base-en §4.4` 逐字依据）：
  `→林晚照 (S1) sings: <d>[中文]月光落在旧琴弦上</d>`
- **一句歌词独立成行，行首 `→`**；严禁写成 `says:`、严禁写成「角色说"…"」、严禁埋在段落中间。
- **MV 不出现 `<Audio N>`** —— 声音全部来自歌曲母带（工作流切窗注入），
  写 `<Audio N>` 会 `LBL-UNDEF`（没有上传对应音频）且与「母带为准」自相矛盾。
- 台词/歌词语言控制四层（外语歌）：
  ① `<d>[Japanese]` 或 `<d>[English]` ② `summary` 声明「全片歌词一律为 X 语言」
  ③ 演唱角色 Subject 写「该角色说/唱日语」 ④ `Negative` 压掉**非目标语言**
  （⚠️ 目标语言是英语时**只**写 `no Chinese dialogue`）。

**C3. 六段式结构一个字段都不能少**（项目视频模型 铁律 1）：
`subject_definitions:` → `summary:` → `retention_analysis:` → `detailed_description:`
→ `overall_soundscape:` → `non_diegetic_music:`，末尾跟 `Negative:`。
- 语言分层：**字段名 / 标签 / 保留标记 / Negative / `(S1)` 说话人 ID / 官方框架词 / R34 表演指导行 / 官方运镜句** 用**英文**；
  **Subject 描述 / summary / retention 正文 / 节拍 / 声场 / 风格句 / 歌词原文** 用**中文**。
- `non_diegetic_music:` 一律写 `N/A`（音乐后期统一配，用户全局偏好；项目视频模型 铁律 32）。
- `overall_soundscape:` 必须写明：**以歌曲母带为准，本段使用原曲第 X–Y 秒的音乐片段**；
  画面内不出现额外人声、不出现对白、不出现第二层人声。

**C4. R34 活人感表演指导行默认必写（唱歌专用模板）。**
- `detailed_description` 的 `[Shot 1]` **之前**、与风格句同段，
  写 `Acting direction for the whole sequence: …`。
- 模板按结构切换（`mv_to_h3_prompts.py` 的 `ACTING`）：`intro` / `chorus` / `bridge` / `outro` / `ambient`。
- **核心判据**：写「她不是在给观众表演，是在对一个人说实话」，
  写呼吸/眨眼/吞咽/手的小动作，**严禁**写「对口型要夸张」「唱给镜头」。
- 纯空镜段豁免（校验器 `LIVE-MISS` / `LIVE-OK` 判）。

**C5. 一段 = 一个场景。**
- 项目视频模型 单段禁止把两个地点写进同一段 —— 实测跨场景同段必丢一整场戏。
- 需要多地点 → 拆段；确需同段多镜头时用官方 `[Shot N]` 写法，
  首镜不加时间戳，后续切点**统一写 `At 00:03.000，`**（英文 `At`，写成「在 00:03.000」解析不出切点）。

**C6. 无主角模式（用户不要主人公时的通道）。**
- 走 `image_mode=text_only`：不建人物资产、关 3 跳过；
  每个 Subject 标「无参考图，由文字描述定义」，保留标记降级 `weak_reference`。
- 全片 `on_screen_char_ids: []`，所有段 `sing_mode=no_sync`，**零 `sings:` 行**。
- 提示词写死 `NO_HERO_DECL`：
  > 本片为**无主角音乐 MV**：全部画面由场景、环境、光影、人群与道具承载，
  > 全片不出现固定主角面孔，任何镜头都不对口型。
- 画面承载靠：环境空镜、群像、道具特写、跟拍背影、自然景观、材质与光影特写。
- ⚠️ 无主角 ≠ 无人物：可以有远景人影/群像/剪影，但**不出现可辨认的固定面孔**。

**C7. 同一段副歌重复出现时必须换视觉处理。**（铁律 C5 的延伸）
- `plan_mv_storyboard.py` 会自动识别重复句簇并标 `in_chorus_block`；
  第二次副歌出现在审核页上必须能看出**与第一次不同的画面构想**，否则重写 `visual_brief`。

### 铁律 D · 工作流与生成

**D1. 工作流注册表驱动，换工作流必须成对换整套节点映射。**
- 注册表：`references/mv_workflows.json`；默认 `MV-1`。
- 新增工作流 = 往注册表加一条 + 放一份 API 格式 JSON，**不改代码**。

**D2. 节点契约（用户 2026-09-17 给定，语义权威）：**

| 节点 | 语义 | 脚本字段 |
|---|---|---|
| **87** | 提示词输入 | `nodes.prompt` / `fields.prompt` |
| **85** | **音乐时长的截取 —— 决定每一次跑多长的视频** | `nodes.music` / `fields.music_start` / `fields.music_dur` |
| **61** | 分辨率（横屏/竖屏），**默认值 2** | `nodes.resolution` / `fields.resolution` |
| **42** | **可改造节点**，按需接收图片 | `nodes.image` / `nodes.img_slots` |

- ⚠️ 这只是**语义**，不是字段名。**字段名必须实测**（铁律 D4）。
- ⚠️ 分辨率默认 **2**（用户指定）；横竖屏的具体取值映射在 `--inspect` 看清值域后填
  `resolution_map`，**不许猜**。

**D2b. 分辨率是「两个入参」，不是一个数字（本项目实测踩雷）。**
- node 61 = `ResolutionSelector`，吃**两个**入参：
  - `aspect_ratio` —— **枚举字符串**，值域来自 ComfyUI 核心节点 `ResolutionSelector`
    的 AspectRatio 枚举。⚠️ **16:9 的字符串是 `16:9 (Widescreen)`，没有 Landscape 字样**
    （凭直觉写成 `16:9 (Landscape Widescreen)` 会被平台判非法枚举）。
  - `megapixels` —— **数字档位**，本项目默认 **2**。
- ❌ 旧实现把「分辨率档 2」这个**数字**注进 `aspect_ratio` 枚举 → 平台收到非法枚举。
  两个入参**必须分开注**（注册表里 `fields.resolution` = `aspect_ratio`、
  `fields.resolution_mp` = `megapixels`）。
- `multiple=32` + `megapixels=2` → 16:9 实算 = **1920×1088**（**不是** 1920×1080），
  首镜试产时用 ffprobe 实测回写 `resolution_measured`。


**D3. 先取真 JSON，再改造 —— 绝不允许按猜测的字段名提交。**
```bash
python references/build_mv_workflow.py --fetch --inspect --write-registry
```
它会：拉 `/api/openapi/getJsonApiFormat` → 体检 87/85/61/42 是否存在 →
猜字段名 → 回写注册表并置 `contract_verified`。
`batch_run_mv.py` 提交前会用 `rh_client.audit_contract()` 再硬校验一次，
**契约不过 = 拒绝提交**（猜错字段名 = 白烧币）。
- 没有 API key 时，用户在 project_provider 导出 API 格式 JSON →
  `--src <文件>` 走同一条路。

**D4. 图槽改造：从图槽节点扩槽 + 未用槽必须断开。**
- ⚠️ **「图片入口」不是 node 42（采样器），而是 node 36 LoadImage**。MV-1 实测：
  `36 LoadImage.image → 42 项目模型.ref_images.ref_image_0`。
  node 42 是**消费端**，node 36 才是**注入端** —— 把文件名注到 42 会报「没有输入字段 image」。
- node 42 原生只吃 1 张图（只有 `ref_images.ref_image_0`）。需要「主角 + 场景/道具」时用
  `--build --image-slots N` 扩槽。
- 脚本只做**安全的节点克隆**（新 LoadImage 节点），**不擅自乱改接线** ——
  接线要在 ComfyUI 里确认（脚本会把「下游是单值输入还是列表输入」报告出来）。
- 未用满的槽**必须断开**，否则会带上工作流作者的默认素材
  → 音频变杂音 / 主角不像本人（drama 铁律 D8 的血泪教训）。
  **MV 里这条尤其致命**：原工作流 node 36 挂着一张**示例人物图**，空镜段不断线
  → 画面里冒出别人的脸（见 D11）。

**D5. 共享模板必须去参考化。**
- 平台共享模板的参考素材入口会残留**上一位使用者**的图/音频直连
  → 人脸服装被污染（drama《世界要毁灭了·日本版》段 3 实测翻车）。
- `build_mv_workflow.py` 默认只**报告**残留，确认后跑 `--drop-refs` 真断开。
- 自建的私有工作流才允许直接带参考素材。换工作流时先问一句「这工作流是共享模板还是我的私有工作流」。

**D6. 提交走 `workflow` 参数直传改造后的完整 JSON**（平台按 workflowId 定位模板、用 workflow 整体覆盖）
→ 节点结构完全可控，不依赖平台上的模板状态。

**D7. 时长贴合 = 音画对齐的工程保证（关键机制，别删）。**
- 请求时长 = `align(窗口长)`（向上对齐 17 帧网格）；音乐窗口 = `[t_i, t_{i+1})`。
- 下载后用 ffmpeg **把每段裁/补到恰好等于窗口长度**：
  - 长了 → `-t 窗口长` 裁掉；
  - 短了 → `tpad=stop_mode=clone` 补尾帧。
- **为什么必须做**：项目视频模型 每段多出 0.1~0.4s，几十段累加下来画面就会漂到音乐后面去，
  口型全废。裁回窗口长度后 **Σ各段 = 全曲长**，首尾相接即对齐。
- 双保险：`final_master.mp4` 用「画面轨 + 原曲母带」重贴并 `-t 曲长`，
  即使前一道有微小残差也被裁掉 → **交付首选这一版**。

**D8. 音乐取用方式二选一，按注册表的 `music_mode` 走。**
- `offset`（首选）：node 85 自带「起点 + 时长」两个入参 → 直接注入秒数，零额外成本。
- `upload`（兜底）：node 85 只有时长、起点不可控 → 驱动脚本用 ffmpeg 按歌词时间轴
  切好本段音频（`音乐/cuts/cut_NN_*.wav`）再上传注入。
- **两种都必须与 `lyrics.json` 同源**，不许手算秒数。

**D8b. 母带本体必须注入音频加载节点（MV-1 = node 34 LoadAudio.audio）。**
- ⚠️ **本项目实测暴露的大坑**：`offset` 模式原来只注 node 85 的「起点 + 时长」，
  **从不替换 node 34 里的示例 mp3** —— 结果是「窗口取对了、歌是别人的」。
  整片 22 段全废，而且烧完币才发现。
- 所以：**与 music_mode 无关，母带都要原样注入 node 34**（铁律 A6 的落地点），
  且全片**只上传一次**（`upload_cached()` 走 sha1 指纹 + `状态/素材上传台账.json`）。
- 参考图同理走缓存 —— 同一张主角图 21 段各传一遍既慢又浪费额度。
- `music_mode=upload` 时，切好的片段要注到**音频加载节点**（34），不是截取节点（85）。

**D8c. 上传台账里绝不允许出现「占位串」——占位串会被原样注进节点，任务当场挂。**
- ⚠️ **本项目实测血泪（首镜 FAILED 的真凶）**：`状态/素材上传台账.json` 里 song.mp3 的
  `fileName` 是 `<上传:song.mp3>`（一个「还没真传」的占位标记），`upload_cached()` 命中缓存后
  把它**原样返回**并注进 node 34 → 平台报
  `LoadAudio → audio - Invalid audio file: <上传:song.mp3>` → 任务 FAILED，白等一轮。
- **判据写死**：project_provider 的 `fileName` 永远长这样 `api/<hash>.<ext>`，
  **绝不以 `<` 开头**。`upload_cached()` 已加守卫：缓存值以 `<` 开头 = 判定「未上传」→ 重新上传。
  自己写状态文件时也不要塞任何「看起来像占位符」的值。
- **通用教训**：**任何「缓存/台账」都可能缓存住一个「未完成状态」**。缓存写入前先问一句
  「这个值是真结果，还是『还没做』的标记？」——两者的区别必须能从值本身看出来（这里是
  `api/` 前缀），不能靠人记。

**D8d. 任务失败必须回挖真实原因，别信 status 的 `code=0 msg=success`。**
- ⚠️ 实测：任务 FAILED 时 `/task/openapi/status` 只回
  `{"code":0,"msg":"success","data":"FAILED"}` —— **真实原因一个字都没有**。
  旧版 `poll_task` 照它抛错，于是报错信息就是一句
  `任务失败: code=0 msg=success`，**等于没报**，人只能靠猜。
- 真实原因藏在 `/task/openapi/outputs`：`code=805 APIKEY_TASK_STATUS_ERROR`，
  `data.failedReason` 里有 `exception_type` / `node_id` / `node_name` / `traceback`。
- 已封装 `rh_client.fetch_failure()` + `format_failure()`，`poll_task` 失败时自动回挖，
  报错形如：`prompt_outputs_failed_validation @ node 34(LoadAudio) → Custom validation failed
  for node ["audio - Invalid audio file: <上传:song.mp3>"]`。
- **排障口径**：拿到 FAILED 先用**那个 taskId** 去 `outputs` 回挖（失败任务的消息不会消失），
  不必重跑烧币。

**D9. 显式记录音频策略。**
- 首镜试产时必须**实测确认**音频取用方式（母带直出 / 项目视频模型 生成音频与母带混合 /
  只出环境声），把结论回写 `mv_workflows.json` 的 `audio_policy` 字段。
- 在确认之前，提示词一律按「以母带为准、不出额外人声」写，并靠 `final_master.mp4` 兜底。

**D10. 并发、断点续跑、在途 rescue、降级留痕。**
- 状态落 `状态/rh_state.json`；`done` 跳过。
- **在途 `submitted` 段一律走 rescue，绝不重新提交**（★ V1.0.3 补实）：
  段一旦已有 `taskId` 就**先拿这个 id 去轮询**，SUCCESS 就下载交付、RUNNING 就继续等、
  FAILED 才重新提交。**旧版会把它当新任务重新提交 = 双倍烧币**；
  这条必须是代码，不能靠人记得（《野心家》首镜失败后是靠人工拿 taskId 回挖才救回币的）。
- `TimeoutError` / `outputs 未就绪` → 状态**保留 `submitted` + taskId**（任务还在平台上跑），
  下次跑自然走 rescue；真失败才置 `failed`（但 taskId 仍保留，便于回挖 `failedReason`）。
- **账号降级（消费级 → 企业级）必须显式授权**（★ V1.0.3 补实）：
  - `--api-key-e <KEY>`（或 `.env` 的 `project_provider_API_KEY_E`）= **提供凭证**
  - `--allow-enterprise-fallback` = **授权花钱**
  - ⚠️ **两件事不能互相推定**：给了 key ≠ 同意烧真钱。没加授权开关时，
    即使提供了企业级 key 也**只打印提示、绝不降级**。- 降级只对**像「池子被占」的错误**生效（`DEGRADE_PAT` 命中 QUEUE/BUSY/LIMIT/并发/占用/余额…）；
  像 `WORKFLOW_NOT_EXISTS` 这种**自己的 bug** 一律不降级 —— **别拿真钱补自己的错**。
- **熔断**：连续 3 次「降级也失败」→ 停手，之后不再尝试（不再白花真钱）。
- 每次降级写 `状态/调度日志.csv`（时间 / 段 / 事件 / 原因 / **计费口径**）
  —— **不留痕就事后算不清「这段烧的是币还是钱」**。
- ⚠️ **企业级不费 供应商报告费用，但按秒扣钱包真钱**（Plus ¥6/小时）。默认一律用消费级。
- 每 10–15 分钟主动汇报进度，**禁止启动后沉默等通知**。
- 离线单测：`python examples/test_account_fallback.py`（零算力、零网络，锁住上面五条判定）。

**D11. 双池并行：消费级 + 企业级**同时**开跑（★ V1.0.4）。**

- 触发：`--enterprise-parallel`。**这是第三个独立开关**，三者关系必须分清、互不推定：

  | 开关 | 含义 | 不推出的结论 |
  |---|---|---|
  | `--api-key-e` | **提供凭证** | ≠ 同意花钱 |
  | `--allow-enterprise-fallback` | 授权「消费级失败 → 改走企业级」 | ≠ 同意并行 |
  | `--enterprise-parallel` | 授权「两条车道**同时**开跑」 | — |

- **机制：一个共享任务队列 + 两条车道同时抢**（消费级 `--workers` 宽 ∥ 企业级 `--workers-e` 宽）。
  为什么不是对半切开：实测单段机器耗时 600~900s 差得很远，静态对半必然一条车道空转；
  谁先空出手谁接着取，墙钟才真的减半（离线单测实测并行度 ≈ **2.0x**）。
- **真钱封顶**：`--enterprise-parallel-max N` = 最多 N 段走企业级，额度用满该车道**退役**、
  剩下的段回消费级。不设就是**不限**；开跑前会打印最坏 / 对半两档预估
  （按实测单段 727s × ¥6/小时 ≈ **¥1.21/段** 折算）。
- **池满 = 没烧钱**（`SubmitBusy`，实测 `{"code":813,"msg":"APIKEY_TASK_QUEUE_FULL"}`）：
  段**放回队列**重试，**绝不记 `failed`**。判据：提交被拒时一分钱都没扣，
  记成失败会让「重跑一次就能成」的段变成需要人工介入。
  ⚠️ 双池模式下池满**不走降级** —— 两条车道同时在跑，正确动作是放回队列让另一条接走；
  本车道自己改走真钱的话，消费级一旦被占，5 个 worker 会把**整片同时甩给企业级 = 全片烧真钱**。
- **「可重试」≠「可降级」**：只有 `TRANSIENT_PAT`（QUEUE/BUSY/TOO_MANY/RATE_LIMIT/OVERLOAD/
  WORKER/并发/占用/排队/繁忙）才是「等一会儿就好」；`余额不足` / `APIKEY_INVALID`
  重试一万次也一样，**不进**这张表（也不该触发降级）。
- ⚠️ **静默丢活是双池并行最阴的一种错**（不报错，只让成片凭空短一截）：
  车道会因「真钱封顶用满」或「池满持续超过 `BUSY_GIVE_UP_SEC`（默认 30 分钟）」**主动退役**，
  而退役那一刻它可能刚把一段 `put` 回队列、另一条车道却早已因「当时队列空」退出 →
  那几段**既没跑也没记 failed**，账面上看不出任何异常。所以车道全停后必须**队列兜底**：
  队列里剩的段一律回落消费级单池跑完。
  > ★ **判据是「等了多久」不是「错了几次」**（V1.0.5 更正）：次数上限对消费级太狠
  > （3 次 ≈ 2 分钟就退役，池子只是有点挤而已，退役反而把活推给兜底路径直接判死），
  > 对「池子真的挂了」又太宽容。**池满就等，等够 30 分钟才交棒**；
  > 且这条**对两条车道一视同仁** —— 否则消费级池满会**无限重试**，进程永远转不停。
- 每次「授权 / 退役 / 池满放回 / 兜底」都写 `状态/调度日志.csv`；
  `状态/成本台账.csv` 新增 **「钱包元」** 列（企业级段的 供应商报告费用为 0，真钱记在这一列）。
- 离线单测：`python examples/test_parallel_lanes.py`（零算力零网络，锁住三条**错了也不报错**的判据：
  「真钱封顶不被绕过」「不许静默丢活」「池子全满时不许挂死」）。

**D12. 凭证跨项目自愈：**永远不问用户要 key**（★ V1.0.6）。**

- **用户原话（2026-09-17）**：「我不是说了把这些key永久记住吗，怎么还找我要？」
  → 根因**不是**记忆丢了（key 早在 2026-09-14 就永久写进 `~/.project_provider/MEMORY.md`），
  而是 `load_dotenv()` 只认「当前项目目录下的 `.env`」—— 换个新项目就找不到、就报缺 key。
- **所以本铁律的判据只有一条**：
  > **写在 `MEMORY.md` 里不算修好，代码能读到才算修好。**
  凡「用户说过一次、以后不该再问」的东西，必须落成**代码可读的持久化文件**。
  只写记忆不写代码 = 下次一定还会再问一遍，而且用户会认为你根本没记。
- 落地：`~/.project_provider/credentials/mv-auto-pipeline/keys.env`（用户级，跨项目），
  与 `<项目根>/.env`（项目级覆盖）、真实环境变量（永不被改写）合成四级读取，见「阶段〇 · 凭证」。
- **两处入口必须同时自愈**：`resolve_key()`（消费级）+ `enterprise_key()`（企业级）。
  只修消费级 = 用户级文件里的企业级 key 形同虚设——要用时照样报「没给企业级 key」。
- **`self_heal` 是无条件加载**，不是「环境变量空才加载」：
  后者会让 `LAST_SOURCE` 留空 → 诊断报告**说谎**（声称不知道来源，其实来自环境变量）。
- **验收动作**：拿一个**全新空目录**，不传 `--api-key`、不放 `.env`，跑 `resolve_key()`
  ——必须读到 key。`python examples/test_credentials.py`（22 条断言，零算力零网络）。

**E2. 每关双关制，用户可放权。**
- ① **Agent 自审** = 机检 + 项目视频模型 官方校验器（错误必须 0）+ 语义审（贴合歌词/口型策略/节拍合理）
- ② **用户 HTML 审** = 逐段可看可改
- 用户说「全自动」/「你自己审」→ **跳过人工那一关，但 Agent 自审 + 机检 + 硬门禁一律保留**。
  放权的是「谁来点头」，不是「要不要检查」。

**E3. 关 5 + 关 6 是硬门禁，全流程唯一挡在「花算力」之前的闸门。**
`batch_run_mv.py` 提交前读 `状态/prompt_review.json` + `状态/music_plan.json` 硬校验：
- 关 5：整体 `status ∈ {approved, partial}` / 逐段 `reviewed_ok` /
  `resolution_confirmed == true` / **逐段 prompt.txt 的 sha1 与审核时一致**；
- 关 6：`music_plan.ok == true` / 逐段窗口与计划一致；
- 任一不满足 → `sys.exit`，**一段视频都不会提交**。
- **改动即重审**：提示词改过 → sha1 失效 → 置回 `pending`，
  **且不静默改写 sha1**（改写了等于默许下次直接放行）。
- 唯一逃生口 `--skip-gate`（仅排障，正常流程禁用）。

**E4. 对齐三验（关 8，`check_alignment.py --verify`）。**
1. **时长**：Σ各段 `output.mp4` 时长 == 原曲长（±0.15s 目标，>0.4s 报错）；
2. **波形**：逐段提取 RMS 包络，在「预期位置 ±1.5s」内做局部相关 ——
   最优滞后量应 ≈ 0s（|滞后| > 0.35s 报错，相关度 < 0.35 报错）；
3. **人声**：对口型段的音频能量必须非空（RMS 阈值）且与母带同位置相关。
- 输出 `视频/final/对齐验收.html`。**任一不过 → 不许说「MV 做完了」。**
- 为什么用「包络 + 局部搜索」而不是原始互相关：213 秒的歌按 8k 单声道接近 1.7M 采样，
  纯 Python 全量互相关是十亿级运算；降到 10 帧/秒的 RMS 包络再局部搜，运算量降到万级，
  **纯标准库秒级出结果**，判据完全够用。

**E5. 审核页必须「齐全 + 最新 + 缺失也显式渲染」。**
- 8 关 ↔ 8 张页，一关不漏；另加 `全链总览.html` 作收尾交付。
- 徽章读**真实状态**（`pipeline_state.json` / `prompt_review.json` / `music_plan.json`），
  不许永远显示「⏳ 待审核」。
- 缺文件时渲染灰底「**未审**」，**不许什么都不显示**。
- 图片/视频用 **`file:///` 绝对路径**（相对路径在 host 预览服务下解析不到 —— 实测踩过）。
- 改了关号/文件名，必须**同步改生成器**（只改文档不改代码 = 没修）。

### 铁律 F · 进化与回退（沿用并强化自 drama-auto-pipeline V1.4）

**F1. 每一支 MV 收尾必须做「项目复盘」（强制，不许省）**
触发时机：关 8 通过 / 用户说「收尾」「完成」。三问逐条回答并落盘 `状态/production_log.md`：
1. **实测 vs 预设**：段数 / 对口型占比 / 时长 / 供应商报告费用 / 耗时，与预期差多少？
2. **本次翻车清单**：哪里报错、哪里返工、哪里手动补了脚本、用户提了什么意见？
3. **可沉淀项**：上面每一条，能不能变成**铁律**（文档）/ **代码改动** / **不变式自检**？
- 判定规则：**只要有一条能沉淀 → 必须当轮就改 skill**，不允许「只记在项目日志里以后再说」。

**F2. 沉淀必须落到「代码 + 文档 + 自检」三处（缺一不可）**
- 代码：改 `references/*.py`，能用 grep 找到 diff（**只写文档不改代码 = 没修**）
- 文档：SKILL.md 铁律正文 + 版本历史，重要改动同步 `CHANGELOG.md`
- 自检：往 `tools/checks.txt` 加一行 `<相对路径>|<关键字>`，**这条修复以后就再也丢不掉了**

**F3. 改完必须发版（唯一收尾动作）**
```bash
python tools/snapshot.py --version <新版本> --kind patch|minor|major \
    --project "《项目名》" --summary "一句话" \
    --item "改了 X，因为 Y" --verify "实测：..." \
    --add-check "references/xxx.py|新关键字"
```
依次：跑 `checks.txt` 回归自检（**老修复丢一条就拒绝发版**）→ 追加 `CHANGELOG.md`
→ 打 `_versions/mv-auto-pipeline-V<版本>-<日期>.zip` 快照 → git commit + `git tag V<版本>`。

**F4. 回退（进化把版本搞坏时的救命绳）**
```bash
python tools/rollback.py --list            # 看所有历史版本（git tag + zip 快照）
python tools/rollback.py --to V1.0         # 退回指定版本
python tools/rollback.py --to V1.0 --from-zip   # git 也坏了 → 用 zip 快照兜底
```
- 回退**前**自动把当前状态备份为 `_versions/_pre_rollback_V<版本>_<时间戳>.zip` → **回退本身也能被回退**。
- 回退动作作为一次**新提交**记录，不重写历史、不 force push。
- ⚠️ 兜底路径（尤其「回退」这种平时不用、出事才用的）**必须在隔离环境主动演练一遍**。

**F5. 向用户汇报的话术（每轮收尾必说）**
- 本次沉淀了什么（改了几处代码 / 几条铁律 / 几条自检）
- 版本号从 V?a.b → V?c.d，回退命令是什么

⑥ 项目视频模型 六段式提示词派生（sings 官方框架 + R34 表演指导）→ ⛔ 关 5（提示词审核 · 硬门禁）
⑦ 音乐窗口与口型对齐核对 → ⛔ 关 6（音乐窗口审核 · 硬门禁）
⑧ 工作流改造（fetch → inspect → 扩槽 → 去参考化）+ 首镜试产
⑨ 批量生成（并发 + 断点续跑 + rescue + 降级留痕 + 时长贴合）

② 真实环境变量 project_provider_API_KEY                    shell 里 export 的，永不被文件改写

文件格式（`ENV_NAMES` 里列出的键才会被读）：

```ini

项目模型_API_BASE=[项目内资源]
```

🔒 **不可动摇的三条**：
1. **`resolve_key()` 必须自愈** —— 调用方忘了 `load_dotenv` 也要读得到（`self_heal=True` 时无条件加载）。
   只做「环境变量为空才加载」是**错**的：环境变量已有时不加载 → `LAST_SOURCE` 留空 → 诊断报告说谎。
2. **`enterprise_key()` 与 `resolve_key()` 同级** —— 只修消费级 = 用户级文件里的企业级 key 形同虚设。
3. **「用户说记住」= 必须落成代码可读的形态**。写在 `MEMORY.md` 里的 key，代码不读就等于没记。
   凡「用户说过一次、以后不该再问」的东西，一律落 `keys.env` 这类**代码可读的持久化文件**，
   而不是只落一句记忆。**判据：新项目、零参数、能跑通。**

诊断（不打印 key 本体，只报「有没有 + 从哪来」）：

```bash
python -c "import sys; sys.path.insert(0,'references'); import rh_client as r; [print(x) for x in r.credential_report('.')]"
```

| 症状 | 真因 | 处置 |
|---|---|---|
| 换项目后报「❌ 缺少 project_provider API Key」 | 用户级 keys.env 不存在或被改坏 | 补 `~/.project_provider/credentials/mv-auto-pipeline/keys.env`；**不要**改成向用户索要 |
| 项目里读到的是旧账号 | 项目 `.env` 覆盖了用户级 | 删该项目的 `.env`，或确认它确实该生效 |
| 企业级 key 读不到（但消费级正常） | 只改了一半 —— `enterprise_key` 没接进读取链 | 两处入口必须同时走 `load_dotenv` |

## 阶段二：歌词提取与强制对齐 → ⛔ 关 1

**这是整条链的地基。地基歪了，后面全白做。**

### 2.1 歌曲探测

```bash
python references/extract_lyrics.py --project-root "<根>" --song "音乐/song.mp3" --probe
```
→ `音乐/song_info.json`（时长 / 采样率 / 声道 / 码率）+ `音乐/song_16k.wav`。

### 2.2 ASR 拿时间（四路后端自动降级）

```bash
python references/extract_lyrics.py --project-root "<根>" --song "音乐/song.mp3" --backend auto
```
优先级：`faster-whisper`（本地推荐）→ `whisper` CLI → `whisper.cpp` → OpenAI 兼容 ASR API。
- 全部不可用时给**明确指引**（不是静默失败）：
  ① `pip install faster-whisper` ② `--backend api --api-base ... --api-key ... --model ...`
  ③ 直接提供现成 LRC 走 `align_lyrics.py --lrc ...`。
- 歌曲语速/和声多，**model-size 建议 `medium` 起**。

### 2.3 官方歌词强制对齐

```bash
# 有官方歌词（推荐）
python references/align_lyrics.py --project-root "<根>" \
  --asr "歌词/lyrics_asr.json" --official "歌词/lyrics_raw.txt" --song "音乐/song.mp3"
# 有现成 LRC
python references/align_lyrics.py --project-root "<根>" --lrc "歌词/lyrics.lrc" --song "音乐/song.mp3"
```
算法：字符级 Needleman-Wunsch 全局对齐（去标点、match +2 / mismatch −1 / gap −1），
把**官方歌词行**映射到 **ASR 字符时间**上；命中率低于 55% 的行标 `review_needed`。
同时：插 `[instrumental]`、跑自检、出 `lyrics.json` / `lyrics.lrc` / `lyrics_review.html`。

### 2.4 ⛔ 关 1：歌词时间轴审核

```bash
python references/audit_html_builder.py --project-root "<根>" --stage lyrics
```
用户看 `审核/01_歌词时间轴审核.html`：逐行「起 / 止 / 时长 / 歌词 / 对齐命中 / 状态」。
**「⚠ 待核」行必须人工听一遍**（这一句是整条链唯一必须人工的地方，别省）。

**通过后**把 `pipeline_state.json.stages.lyrics.status` 置 `approved`，才允许进关 2。

## 阶段五：MV 分镜设计 → ⛔ 关 4

### 5.1 歌曲线切段

```bash
python references/plan_mv_storyboard.py --project-root "<根>" --target-dur 11 --sync-ratio 0.45
```
它做四件事：
1. **切段**：按歌词时间轴切，窗口连续、切点只落在歌词行尾、段长落 [4,15]
2. **口型策略**：按 `sync_ratio` 等距抽样 → 标 `sing_mode=sync|no_sync`、
   定 `shot_size`（sync 只能取 ECU/CU/MCU/MS，no_sync 取 MS/MLS/LS/WS/EMPTY）、
   拆开连续 ≥3 的 sync 段
3. **结构识别**：重复句簇 = 副歌，标 `in_chorus_block`（供 C7 视觉变奏用）
4. **机检**：窗口连续 / 段长合法 / 口型-景别一致 / 歌词不越窗 → 不过就报出来

> ⚠️ **两个区间别混**（V1.0.1 踩过）：
> - **项目视频模型 硬区间 `[4,15]` 秒** —— 段长必须落在这里。这是本铁律 C1 的口径，
>   也是 `cut_segments(min_dur=4.0)` 的契约，关 6 同样按 `4.0/15.0` 核。
> - **请求时长区间 `[5,15]` 秒** —— 下限是 5.0 而非 4.0，因为 17 帧公式带 `max(5, …)`：
>   窗口只有 4~5s 时实际请求 5s 出头，成片再裁回窗口长度（正常，不是错误）。
>
> 曾经 `qc()` 把硬边界写成 `MIN_REQ - 0.3`（= 4.7s），结果 **4.0~4.7s 的段合法产出却被判死**
> ——校验器假阳性。**判「段长是否合法」只认 `[4,15]`；`4~5s` 只提示、不拦。**

### 5.2 主 Agent 必须补的字段（脚本给不出画面）

| 字段 | 说明 |
|---|---|
| `visual_brief` | **中文导演画面构想**：这一段画什么、机位在哪、光从哪来、人物是什么状态 |
| `shots`（可选） | 段内镜头表 `[{t, size, zh}]`。不给就自动切（sync 段按歌词行 ≤3 镜，no_sync 段 ≥9s 切 2 镜） |
| `ending_zh` | 收势：段末停在什么姿态（下段的起始锚点） |
| `next_cut_zh` | 下段切点：切到什么景别/视点 |
| `scene_id` / `prop_ids` | 本段用到的场景/道具 |
| `crowd` | 场景天然含群众（街拍/演唱会/食堂）→ true，自动加背景人群三锁定 |
| `duet` | 双人对唱 → true，发声行写 `(S1,S2) sings:` |

**视觉变奏要求（C7）**：同一段副歌第二次、第三次出现时，
`visual_brief` **必须**与首次不同（换景别/换空间/换光比/换主体），否则重写。

### 5.3 ⛔ 关 4 审核
`--stage storyboard` → `审核/04_分镜审核.html`：
逐段「音乐窗口 / 时长 / 结构 / 口型 / 景别 / 歌词 / 画面构想」+ 口型规则提示条。

- 消费级被占 → 单池模式：经显式授权后降级企业级；双池模式：**放回队列**（池满没烧钱）。

**成本口径**（实测规律，收尾汇报必须写明）：
- 消费级 **0.4 供应商报告费用 / 秒耗时**；企业级 **¥6 / 小时耗时**；**按墙钟秒计费、含排队、与视频时长无关**。
- 余额：`POST /uc/openapi/accountStatus`（⚠️ 参数名小写 **`apikey`**）→ `remainCoins` / `remainMoney` / `apiType` / `currentTaskCounts`。
  ⚠️ **`currentTaskCounts` = 此刻正在跑的任务数，不是并发额度**（★ V1.0.4 更正）
  —— 两把 key 在无任务时都返回 `0`；账号能开多大并发**没有接口能读**，
  只能靠「池满就放回队列」这种自适应写法兜住。
  `apiType` 才决定计费口径：`NORMAL` = 消费级走 供应商报告费用；`SHARED` = **按秒扣钱包真钱**；
  同一账号的两把 key 会指向**同一个钱包**（余额数字完全相同）。
- 逐任务：`POST /task/openapi/outputs` → `consumeCoins` / `consumeMoney` / `taskCostTime`。
- 币/元比值**从账号现算**，不许写死。
- **只给数值的页面，用户一定会回来问** → 任何「花了多少 / 慢了多久」的页，必须
  **数值 + 出处 + 可复核算式** 三件齐全。

```bash

```
三验（铁律 E4）：**时长**（Σ各段 = 曲长）/ **波形**（最优滞后 ≈ 0s、相关度达标）/
**人声**（对口型段能量非空）。任一不过 → **不许说「MV 做完了」**。

常见问题与处置：

| 现象 | 根因 | 处置 |
|---|---|---|
| 某段滞后 > 0.5s | 该段 `output.mp4` 没走 conform / 窗口与计划不一致 | 查 `log.json.conform`；重跑该段 |
| 波形相关度普遍偏低 | 音频整体不是母带（工作流在生成自己的音频） | 以 `final_master.mp4` 为准；同时把 `audio_policy` 记进注册表 |
| 对口型段能量过低 | 该段其实没出声（项目视频模型 没唱） | 检查 `sings:` 行是否独立成行、是否被 `says:` 污染；重抽 |
| 不对口型段的嘴在动 | `NO_SYNC_DECL` 未生效 | 强化 Negative + 把该段改成**中远景/背影/空镜**（换景别比改提示词更稳） |
| Σ各段 ≠ 曲长 | 有段落没跑完 / conform 失败 | 补齐后重新拼接 |
| 报错只有 `任务失败: code=0 msg=success` | status 端点失败时**不给原因** | 用该 taskId 调 `outputs` 回挖 `data.failedReason`（`fetch_failure()` 已自动化）——**不用重跑烧币** |
| `Invalid audio file: <...>` | 台账里存的是占位串，被原样注进音频节点 | 清掉该条缓存重传（`upload_cached()` 已加 `<` 前缀守卫，见 D8c） |
| 空镜段画面里冒出人脸 | node 36 的示例图没断线，且走的是 nodeInfoList | 走 `bake_workflow()` 摘线 + `workflow` 整包直传（见 D4/D11） |

## 错误处理与恢复

| 场景 | 处置 |
|---|---|
| 拿不到官方歌词 | 走纯 ASR，全部行标 `review_needed`，**逐行人工过一遍**；实在不行让用户手打 LRC |
| ASR 后端全不可用 | 给三条明确指引（装 faster-whisper / 用 ASR API / 提供 LRC），不许静默失败 |
| 歌词时间轴有空档 | 自动插 `[instrumental]`；空档段一律 `no_sync` + 空镜/群像 |
| 段长算完不落 [4,15] | 调 `--target-dur`；单行歌词占满一段的极短段 → 与邻段合并 |
| 某句歌词被切成两半 | 切点只落行尾（算法已保证）；真需要跨界 → `<scenetrans>` + summary 声明 |
| 工作流契约对不上 | `--inspect --node <id>` 看真实字段名 → 手工改注册表 → 重跑 `--write-registry` |
| 提交被门禁拦下 | 按提示回关 5 / 关 6 补审；**别用 `--skip-gate`** |
| 消费级被占用 | 需用户显式授权才降级：`--api-key-e` + `--allow-enterprise-fallback`；降级写调度日志。**先告知用户「这是拿真钱换速度」** |
| 想用两把 key 一起跑（墙钟减半） | `--enterprise-parallel`（**第三个独立开关**，不能由前两个推定）+ 建议 `--enterprise-parallel-max N` 给真钱封顶；池满只会「放回队列」，不烧钱 |
| 换新项目后报「❌ 缺少 project_provider API Key」 | 用户级 `keys.env` 缺失/被改坏，**不是**「用户没给 key」→ 补 `~/.project_provider/credentials/mv-auto-pipeline/keys.env`（铁律 D12）。**禁止**回头找用户索要；跑 `examples/test_credentials.py` 自证已修 |
| 抽卡不满意 | `--only N --new-seed`；MV 各段零依赖，可多段并行 |
| 音画对不齐 | 先看 `log.json.conform`，再看 `audio_policy`；实在不行以 `final_master.mp4` 交付 |
| 无主角模式某些段显得空 | 用环境空镜 / 群像 / 道具特写 / 跟拍背影填充；必要时**调小 `--target-dur` 增加切镜密度** |

## 版本历史

- **1.0.6（2026-09-17）凭证跨项目自愈：永远不再问用户要 key**
  - **触发（用户原话）**：「我不是说了把这些key永久记住吗，怎么还找我要？」
  - **根因**：key **早就永久记住了**（2026-09-14 即写入 `~/.project_provider/MEMORY.md`），
    但 `rh_client.load_dotenv()` 只认「当前项目目录下的 `.env`」——
    换个新项目 → 找不到 → `resolve_key()` 抛「❌ 缺少 project_provider API Key」。
    **记忆没丢，是代码不读。**
  - **判据升级（本版最重要的一条）**：
    > **写在 `MEMORY.md` 里不算修好，代码能读到才算修好。**
    凡「用户说过一次、以后不该再问」的东西，必须落成**代码可读的持久化文件**。
  - **落地**：新建用户级凭证 `~/.project_provider/credentials/mv-auto-pipeline/keys.env`
    （与既有 `credentials/meituan-living-deals-assistant/token.json` 同规矩），
    读取链升级为**四级**：`--api-key` > 真实环境变量（永不被改写）> `<项目根>/.env`（项目级覆盖）
    > 用户级 `keys.env`（跨项目兜底）。
  - **`resolve_key()` 加 `self_heal`（无条件加载）** —— 调用方忘了 `load_dotenv` 也读得到。
    写成「环境变量为空才加载」是**错**的：会让 `LAST_SOURCE` 留空、诊断报告说谎。
  - **`enterprise_key()` 同级改造**：只修消费级 = 用户级文件里的企业级 key 形同虚设
    （要用时照样报「没给企业级 key」）。`build_mv_workflow.py` 无显式 `load_dotenv`，
    正是靠 `resolve_key` 的自愈才读得到。
  - **`_INJECTED` 快照**：排除「本模块自己注入过的键」，否则第二次 `load` 会把自己上次写的
    当成「真实环境变量」→ 项目级再也覆盖不了用户级。保证幂等。
  - 新增离线单测 `examples/test_credentials.py`（**22 条断言**，零算力零网络零真钱），
    核心断言是「**全新空目录 + 无 .env + 不传任何 key → 必须自愈读到**」；
    另锁「项目级覆盖用户级」「真实环境变量最高」「幂等」「报错文案指向实际凭证路径」。
  - 新增铁律 **D12**；`checks.txt` 新增 30 条不变式（此前**一条凭证相关自检都没有**——
    这正是「记了却读不到」能潜伏至今的原因）。

- **1.0.5（2026-09-18）池满退役改成「限时」而不是「限次」**
  - V1.0.4 发出去几分钟后发现池满处理会把进程**挂死**：判据写的是「连续 3 次池满退役」，
    而且**只让企业级退役** → ① **消费级池满会无限重试**（池子真满了就永远转不停，没有任何出口）；
    ② 反过来 3 次（≈2 分钟）就退役**又太狠**（池子只是有点挤，退役反而把活推给兜底路径直接判死）。
  - **判据错在「次数」**：该看的是「等了多久」。新增 `BUSY_GIVE_UP_SEC`（默认 **30 分钟**，0 = 永不放弃）
    + 每车道 `busy_since`；池满持续超时 → 退役、队列交兜底，**两条车道一视同仁**；
    某次提交成功即把 `strikes` 与 `busy_since` 一起清零。
  - **单测新增 ④b：两条车道**全都**池满** —— 只测「一条退役」测不出挂死。断言秒级收敛且
    4 段最终全部由兜底跑完（实测 **1.4s 收敛**）。
  - 退役原因写实：打印实际等待秒数并写 `状态/调度日志.csv`，取代原来语焉不详的「连续 3 次池满」。

- **1.0.4（2026-09-18）双池并行：消费级 + 企业级同时开跑（真钱可封顶，且不许静默丢活）**
  - **需求**：用户「消费级+企业级一起并行」—— 要的不是「失败才降级」，是**两条车道同时开工**。
  - **机制**：`--enterprise-parallel` 开启后，**一个共享任务队列 + 两条车道同时抢**
    （消费级 `--workers` 宽 ∥ 企业级 `--workers-e` 宽）。
    为什么不用「对半切开」：实测单段机器耗时 600~900s 差得很远，静态对半必然一条车道先空转；
    共享队列让「谁先空出手谁接着取」，墙钟才真的减半 —— 离线单测实测并行度 **≈2.0x**。
  - **第三个独立开关**：`--api-key-e`（提供凭证）/ `--allow-enterprise-fallback`（授权降级）/
    `--enterprise-parallel`（授权并行）**三者互不推定**。只给 key 不等于同意花钱，
    同意降级不等于同意并行。
  - **真钱封顶**：`--enterprise-parallel-max N` = 最多 N 段走企业级，用完该车道**退役**、
    剩下的回消费级。开跑前打印最坏 / 对半两档预估（实测单段 727s × ¥6/h ≈ **¥1.21/段**）。
  - **池满 = 没烧钱** → 新增 `SubmitBusy`：段**放回队列**重试，**绝不记 `failed`**。
    ⚠️ 双池模式下池满**不走降级** —— 两条车道同时在跑，本车道改走真钱的话，
    消费级一被占就会把**整片同时甩给企业级 = 全片烧真钱**。
  - **「可重试」≠「可降级」**：新增 `TRANSIENT_PAT`（QUEUE/BUSY/TOO_MANY/RATE_LIMIT/
    OVERLOAD/WORKER/并发/占用/排队/繁忙）；`余额不足`、`APIKEY_INVALID` 重试一万次也一样，
    **不进**这张表。
  - ⚠️ **静默丢活**（双池最阴的错，不报错、只让成片短一截）：企业级车道会因「真钱封顶用满」
    或「连续 3 次池满」**主动退役**（★ V1.0.5 已把这条判据改成「池满持续超过 `BUSY_GIVE_UP_SEC`」，
    理由见上；此处保留原文以便对照），退役那一刻可能刚把一段放回队列，而消费级车道早已因
    「当时队列空」退出 → 那几段**既没跑也没记 failed**。修法：车道全停后**队列兜底**，
    把队列里剩的段一律回落消费级单池跑完。
  - **台账能加列了**：`append_csv` 原来只要文件存在就直接 `writerow`，而 `DictWriter` 对
    「row 里有、fieldnames 里没有」的键会 raise —— **给台账加一列 = 让跑过的项目再跑一次就崩**。
    改为**自动升级表头**（老列顺序在前、新列补末尾、缺的填空），老行不丢。
    新增「**钱包元**」列：企业级段的 供应商报告费用为 0，真钱记在这一列。
  - **口径更正**：`currentTaskCounts` 是**此刻正在跑的任务数**，不是并发额度
    （无任务时两把 key 都返回 `0`）—— 之前记的「消费级支持 5 并发」是误读；
    账号并发上限**没有接口能读**，只能靠「池满放回」自适应兜住。
  - **测试基建**：`BUSY_BACKOFF_BASE` / `SUPERVISE_TICK` 提成模块常量
    （否则单测测「连续 3 次池满退役」要真等 2 分钟、任何并行测试墙钟下限 5s）。
  - **V1.0.5 补正**：池满退役判据由「次数」改为「持续时长」（`BUSY_GIVE_UP_SEC`，默认 30 分钟），
    并**对两条车道一视同仁** —— 原写法只让企业级退役，消费级会**无限重试**（进程挂死）。
    单测新增 ④b：两条车道**全都**池满时也必须在秒级收敛，不能转不停。
  - **新增离线单测** `examples/test_parallel_lanes.py`（零算力零网络）：
    ①池满→`SubmitBusy` ②`run_one` 三态不写 `failed` ③**真钱封顶不被绕过**且全部段跑完
    ④**池满退役后不许静默丢活** ⑤两车道真的同时在跑 ⑥台账加列不崩 ⑦留痕齐全。

- **1.0.3（2026-09-18）补实两处「文档承诺过、代码里根本没有」的功能：在途 rescue + 企业级降级**
  - **背景**：用户提供企业级 key 时顺带核查，发现**两处文档与代码不一致**（老账：drama 也踩过
    同类坑）——`D10` 写着「在途任务走 rescue」和「消费级被占自动降级企业级」，
    而代码里：`status=submitted` 的段**会被当新任务重新提交**（**双倍烧币**），
    `--api-key-e` **从未被引用**（`args._pool_name` 硬编码 `"consumer"`，
    `状态/调度日志.csv` 从不生成）。**文档承诺 ≠ 代码实现。**
  - **补实 ①在途 rescue**：段一旦有 `taskId` 就**先拿它去轮询** —— SUCCESS 就下载交付、
    RUNNING 就继续等、FAILED 才重提。`TimeoutError` / `outputs 未就绪` 时状态**保留
    `submitted` + taskId**（任务还在平台上跑），下次跑自然接上；真失败才置 `failed`
    （taskId 仍保留，便于回挖 `failedReason`）。
    > 这条必须是**代码**，不能靠人记得 ——《野心家》首镜失败后，是靠人工拿 taskId
    > 回挖 `failedReason` 才定位到根因、把币救回来的。
  - **补实 ②企业级降级**：`--api-key-e`（提供凭证）+ `--allow-enterprise-fallback`（授权花钱）
    **两个开关分开**，因为**「提供凭证」和「授权花钱」是两件事，不能由前者推定后者**。
    没加授权时即使给了企业级 key 也**只打印提示、绝不降级**。
  - **降级只对「池子被占」类错误生效**：新增 `DEGRADE_PAT`
    （QUEUE/BUSY/LIMIT/TOO_MANY/RATE/OVERLOAD/WORKER/APIKEY_/并发/占用/排队/余额/超出/繁忙）。
    像 `WORKFLOW_NOT_EXISTS` 这种**自己的 bug 一律不降级** —— **别拿真钱补自己的错**。
  - **熔断**：连续 3 次「降级也失败」→ 打印警示并停手，之后不再尝试企业级。
  - **留痕**：每次降级写 `状态/调度日志.csv`（时间 / 段 / 事件 / 原因 / **计费口径**），
    否则事后算不清「这段烧的是币还是钱」。
  - **每段各自记账**：去掉全局 `args._pool_name`（多线程会互相污染），
    `pool` 变成 `run_one` 的局部变量，并落进 `log.json` / `rh_state.json` / 成本台账的「账号」列；
    企业级段的钱包消耗另记 `money` 字段。
  - **新增离线单测** `examples/test_account_fallback.py`（**零算力、零网络**）：
    把四种判定钉死 —— ①未授权必拒 ②错误不像「池子被占」必拒 ③授权+池子被占才降级并留痕
    ④连续 3 次降级失败必熔断。**离线冒烟测试永远碰不到这条烧钱分支，所以必须单独测。**
  - **验证**：单测 **6/6 通过**；真实 rescue 实测 —— 用段 22 的**真实 taskId** 把状态改成
    `submitted` 后重跑，日志出现 `♻ 段 22 发现在途任务 … → rescue` 且**没有 `[submit]`**
    （= 确认没有重复烧币），并正常下载 + 按帧贴合到 14.5s；
    `tools/checks.txt` **128 条不变式全通过**。

- **1.0.2（2026-09-18）《野心家》实跑复盘：把「全链能不能真跑通」的五个隐藏坑全部打掉**
  - **修坑 ①（会毁全片）母带从未注入音频加载节点**：`offset` 模式原来只注 node 85 的
    「起点 + 时长」，**从不替换 node 34 LoadAudio 里的示例 mp3** → 「窗口取对了、歌是别人的」，
    22 段全废且要烧完币才发现。新增 `song_path()` + `upload_cached()`：**与 music_mode 无关，
    母带都原样注入 node 34，且全片只上传一次**（sha1 指纹 + `状态/素材上传台账.json`）。
  - **修坑 ②（首镜 FAILED 的真凶）上传台账缓存住了「未完成状态」**：台账里 song.mp3 的
    `fileName` 是个占位串 `<上传:song.mp3>`，被 `upload_cached()` 原样返回并注进 node 34 →
    平台报 `LoadAudio → audio - Invalid audio file: <上传:song.mp3>`。
    **判据写死**：RH 的 fileName 永远形如 `api/<hash>.<ext>`，**以 `<` 开头的一律判「未上传」并重传**。
    > 通用教训：**任何缓存都可能缓存住一个「未完成状态」**；写入前先问「这个值是真结果，
    > 还是『还没做』的标记」——两者的区别必须**能从值本身看出来**，不能靠人记。
  - **修坑 ③（报错被吞）任务失败拿不到真实原因**：FAILED 时 `/task/openapi/status` 只回
    `{"code":0,"msg":"success","data":"FAILED"}`，旧版照它抛错 → 报错信息就是
    `任务失败: code=0 msg=success`，**等于没报**。真实原因在 `/task/openapi/outputs`
    （`code=805 APIKEY_TASK_STATUS_ERROR`）的 `data.failedReason`（含 node_id / traceback）。
    新增 `rh_client.fetch_failure() / format_failure()`，`poll_task` 失败自动回挖。
    **排障口径：拿到 FAILED 先用那个 taskId 回挖，不用重跑烧币。**
  - **修坑 ④（分辨率）把「档位数字」注进了枚举字段**：旧实现把「分辨率档 2」这个**数字**
    注进 node 61 的 `aspect_ratio` → 平台判非法枚举。分辨率其实是**两个入参**：
    `aspect_ratio`（枚举字符串，16:9 = `16:9 (Widescreen)`，**没有 Landscape 字样**）+
    `megapixels`（数字档位，本工作流默认 2），必须**分开注**。实测 2MP@16:9 = **1920×1088**。
  - **修坑 ⑤（空镜段泄漏别人的脸）**：原工作流 node 36 挂着**示例人物图**，空镜段只走
    `nodeInfoList` 时那张图会被当成本段参考。新增 `bake_workflow()`：**把注入烧进工作流 JSON +
    摘掉指向图槽的连线 + 用 `workflow` 整包直传**（rh_client 在给了 workflow 时根本不发
    nodeInfoList），并顺手剥掉本地 API JSON 里的 `_meta`（真 API 格式没这个键）。

- **1.0（2026-09-17 首版）** 用户需求原话：「参考 drama-auto-pipeline 生成一个新的 skill（不要动原 skill），
  全自动音乐 MV 制作 skill，输入一首歌（必须）+ 一张主人公图（可选），自动提取歌词并据此做分镜，
  分镜定下后按需做资产、改造工作流（AI音乐MV数字人 项目模型+项目模型 项目视频模型 项目模型，节点 87/85/61/42），
  最终交付一条口型-画面-音乐全对齐的完整 MV。」
  - **八条铁律体系 A~F**：A 音乐基准与歌词 / B 口型策略 / C 分镜与提示词 /
    D 工作流与生成 / E 审核与对齐验收 / F 进化与回退（沿用并强化自 drama V1.4）
  - **三件事从需求直接固化为铁律**：
    ① 「音乐是唯一时间基准」—— 段长/切点全部从歌词时间轴推导（A1/A5）
    ② 「只有中近景才对口型，且不是每句都对口型」—— 景别白名单 + 占比区间 + 硬机检（B1/B2/B3/B4）
    ③ 「唱歌不是说台词」—— 发声行走官方 `sings:` 框架，**MV 不出现 `<Audio N>`**（C2）
  - **两个原创机制**（本 skill 相对 drama 的核心增量）：
    - **时长贴合**（D7）：请求时长向上对齐 17 帧网格、成片裁/补回窗口长度 →
      Σ各段 = 全曲长 → 首尾相接即对齐。**不这么做，几十段累加就会漂到音乐后面。**
    - **对齐三验**（E4）：时长 / RMS 包络局部相关（滞后 ≈ 0s）/ 人声能量。
      用「包络 + 局部搜索」替代原始互相关，**纯标准库秒级出结果**。
  - **8 道审核关**（比短剧多一道歌词时间轴、多一道音乐窗口与口型对齐），
    关 5 + 关 6 双硬门禁挡在花算力之前。
  - **10 个自包含脚本**（纯标准库，不依赖 numpy/torch）：
    `rh_client` / `extract_lyrics` / `align_lyrics` / `plan_mv_storyboard` /

    `audit_html_builder` + `mv_workflows` 注册表。
    **歌词强制对齐用字符级 Needleman-Wunsch（纯 Python DP）**，官方歌词定文本 + ASR 定时间。
  - **四个 project_provider 客户端口径坑**（从实战带来，别再踩）：
    `accountStatus` 参数名是小写 **`apikey`**；`outputs` 返回 `code=804` 时 `data` 是 dict 不是 list；
